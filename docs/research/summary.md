# Research brief: summary

Generated 2026-11-02 by the research workflow (18 agents: 7 sweeps, 5 adversarial verifications, synthesis, critic, 3 gap fills, final revision). Full text: [brief.md](brief.md).

## Recommended architecture

Option A: a macOS-native Swift app (SwiftUI/AppKit menu-bar shell via NSStatusItem + NSPopover, minimum macOS 15) built on ScreenCaptureKit with the OS cursor hidden, a 120 Hz input-telemetry stream (pointer, clicks, cursor-shape hashes, keystrokes, take markers, shell events) stamped on the host clock and written as versioned JSON, a fragmented long-GOP hardware HEVC/H.264 source file (keyframes every 0.5–1 s by frame count and 2 s by duration via VTCompressionSession, no B-frames, finalized to progressive MP4 at stop), one Metal compositor shared bit-for-bit by preview and export, an editor decoder built from a keyframe index + byte-budgeted frame cache + positioned AVAssetReader pool with failure checks, VideoToolbox export (2 s export GOP, HEVC/H.264/ProRes/HEVC-with-alpha, FFmpeg palette GIF), on-device Studio Sound (vendored xiph/rnnoise, BSD-3) with BS.1770 leveling to −16 LUFS / −1 dBTP, and WhisperKit/Apple Speech captions. Area capture uses the direct ScreenCaptureKit consent path (app overlay + SCContentFilter(display:) + sourceRect; the system picker has no region mode), with the picker held behind a flag for display/window until the three permission tests pass. The effects engine (cursor spring, zoom planner, re-timing, retake matcher, timeline sampler) lives in a UI-free Swift module with golden test vectors and JSON schemas so it can be ported to Rust/wgpu later; no Swift↔Rust FFI in v1. Licensed Apache-2.0 with DCO, Cap kept as a spec-only AGPL reference under clean-room discipline, distributed as a notarized DMG with Sparkle 2 and a Homebrew cask. Fallback if cross-platform becomes mandatory before v1: Rust core + native shells or GPUI (Cap's path), not Tauri.

## Top risks

- macOS consent UX: the system picker cannot do area capture, so area mode forces the one-time Screen Recording TCC grant plus relaunch and the periodic 'bypass the system private window picker' alert (interval unpublished, still shipping on 26.7); the hybrid picker+sourceRect path is untested, and macOS 27 adds a Remote Desktop TCC category and makes CG capture APIs return gray images.
- Editor decode and export reliability at 4K60: AVAssetReader fails mid-stream with -11821 under concurrent sessions and can serve stale frames (Cap #2872, #1787, #1940); 4K per-frame decode cost is unmeasured (1080p figure x4 is an assumption), a 256 MiB cache holds only ~21 4K frames, and the GOP/bitrate/seek trade-offs have to be tuned on real fixtures.
- A/V sync and timestamping under VFR capture, pause/resume and 120/144 Hz displays is the dominant bug class in every shipping recorder (every Cap release Jan-Oct 2026 carries a timing fix; cursor drift #2144 still open); storage I/O stalls can also drop 10% of frames (Cap #2366).
- Mac-only scope limits the open-source community (the 30k+-star projects are all cross-platform) and leaves Windows/Linux DevRel users out; the portable-engine discipline can erode under schedule pressure, making a later port expensive.
- Cursor-shape fidelity after macOS 27: NSCursor.currentSystem is deprecated with no replacement for reading another app's cursor image, so the re-rendered cursor may need heuristics (AX role under pointer, reference capture) that fail in some apps.
- Codec licensing: recommending HEVC as the source codec raises whether an app calling the OS encoder is 'HEVC Software' under Access Advance's public rate card; Via LA's AVC 'unit' definition for free downloads is undefined; gifski is AGPL and any bundled FFmpeg must stay LGPL.
- Automated edits that silently damage content: retake detection, filler removal and redaction can stitch takes, delete real words or miss secrets (Descript's documented failure modes; OCR/regex false negatives), which for a cloud/AI company's DevRel output is a reputational risk unless every automated edit has a review-before-apply UI and a secrets report.
- Auto-zoom quality and motion sickness: there is no primary research on comfortable zoom/pan thresholds, click-only triggers miss terminal/IDE work, and caret geometry via Accessibility is patchy (Ghostty AX support still a draft), so the signature DevRel differentiator depends on per-terminal integration work and user testing.
- Hardware and thermal headroom: 4K60 real-time HEVC encode, 100-400 Mb/s sustained writes and a 4K Metal compositor with blur/shadow/motion blur are unbenchmarked on base M1 and Intel Macs (Screen Studio's Intel/AMD black-editor regression shows Intel needs explicit coverage).
- Maintenance and exit: company-sponsored recorders decay fast without a funded maintainer (Kap shipped an EOL Electron in its last release); Developer ID certificates, notary credentials and Sparkle keys are company assets whose revocation can brick installed copies (Atom), so governance and hand-off must be settled before launch.

### product

### competitors

The Screen-Studio-style recorder space exploded between late 2025 and late 2026: OpenScreen (Electron, MIT) went from zero to 40k stars in a year and was archived on Oct 17, 2026 (community fork getopenscreen/openscreen continues, v2.1.2 Oct 19, 2026); Recordly (Electron+PixiJS, AGPL-3.0, 35.9k stars since Mar 2026) is now the dominant cross-platform OSS option; and Cap (AGPLv3, 24.3k stars) is the most deeply engineered, having just deleted its Tauri/SolidJS UI (PR #3529 merged Oct 29, 2026) in favor of a native Rust + GPUI app on a pinned Zed fork. Cap's 51-crate workspace is effectively a reference architecture for the builder: ScreenCaptureKit via a cidre fork on macOS, Windows Graphics Capture/Direct3D11 + Media Foundation on Windows, PipeWire/xdg-portal/x11rb on Linux, wgpu 25 + glyphon + tiny-skia for rendering, VideoToolbox/Media Foundation/ffmpeg-next-fork/gifski for encoding, whisper-rs and parakeet-rs for captions, and a cpal fork for audio. Cap's effects are mature but purely heuristic: cursor smoothing is a ~1,000-line closed-form spring-mass-damper sampled at 60 Hz with shake filtering, Default/Snappy/Drag profiles and a 500 ms click look-ahead; auto-zoom is click-only with hardcoded 300 ms pre / 2.5 s post / 2.5 s merge / 2.0x defaults, and the camera follows greedy clusters of mouse moves through an 8 ms spring timeline, which users say over-merges fast click sequences (#2928) while a cursor-drift bug on long recordings (#2144) remains open. The hard problems Cap's maintainers and changelog surface are not the effects themselves but A/V sync and timestamp handling (every release from Jan to Oct 2026 carries a timing fix), webview inconsistency across OSes (the stated reason for the GPUI rewrite, which cut editor-playback CPU 76.6% to 17.5% and memory 3,724 MiB to 440 MiB in Cap's own benchmark), Windows timer granularity starving the export pipeline, hardware-encoder fallbacks, Linux's lack of an OS-level H.264 encoder, and macOS 26 regressions. On the commercial side, Screen Studio stays Mac-only and subscription-only ($9/mo yearly, $29/mo monthly, no Windows plans) and just shipped 4.0 (<=Oct 5, 2026: transcript editing, local AI upscaler) and 4.1 (~Oct 26, 2026: on-device PII/face redaction, ProRes, in-house H.264 encoder); CleanShot X 5.0 (Sep 1, 2026) added Studio Mode with Smart Zooms for $35 one-time; Loom still lists auto-zoom as "coming soon"; Descript and Kommodo have no auto-zoom; Kap has had no release since Oct 27, 2022; Recordit shut down Mar 31, 2024. A dozen-plus pay-once Mac/Windows apps ($19 to $199: Screen Charm, Smooth Recorder, CursorClip, ScreenKite, Tight Studio, Canvid, SmoothCut, AutoZoom, Rapidemo, ZoomCap, Cursorful, FocuSee) converge on the identical feature set, so differentiation has moved to on-device captions, Windows/Linux support, export speed, privacy redaction, and CLI/agent integration (Cap CLI+MCP, OpenScreen headless CLI, ScreenKite agent editing). Linux remains the clearest gap: only proprietary Hosaka Studio and Screenix ($39 to $79) and the Electron OSS tools target it, and Cap has open Wayland cursor-capture bugs. For a DevRel team, VHS (MIT, 21k stars, scripted terminal GIFs/MP4s with a CI action) and asciinema 3.x are the complementary dev-demo tools worth integrating rather than rebuilding. License hygiene matters for an open-source plan: Cap, Recordly and OpenScreenStudio are AGPL; OpenScreen, Kap, ScreenCraft, VHS and the windows-capture crate are MIT; obs-zoom-to-mouse has no license at all.

### mac-stack

The native macOS stack is mature enough to build a Screen-Studio-class recorder in Swift with no third-party capture code: ScreenCaptureKit (SCK, macOS 12.3+) delivers IOSurface-backed CMSampleBuffers with per-frame metadata, system audio (13.0+), microphone (15.0+), HDR (15.0+), and a straight-to-file SCRecordingOutput (15.0+), while AVFoundation/VideoToolbox handle camera, A/V clocks, and hardware H.264/HEVC/ProRes encode. Note that as of today (2026-11-02) Apple's docs already show macOS 27 ("Golden Gate", shipped Sept 2026) and the 27 SDK brought SCK to iOS/tvOS/visionOS plus SCClipBufferingOutput and SCRecordingEditor; the team's 15/26 target is fine but the 27 changes (and the macOS 27 deprecation of NSCursor.currentSystem) affect architecture. The key design decision is SCStream + your own AVAssetWriter versus SCRecordingOutput: the latter is trivial but exposes only URL/file type/codec (no bitrate or quality control, and one Oct 2025 report of washed-out ~720p-looking output), so an effects-focused tool should capture via SCStream, record cursor telemetry separately, and render/export itself. The proven pattern across every recent open-source Swift project (Reframed MIT, SmoothCursor, Screenize Apache-2.0) is: hide the system cursor (showsCursor=false), log pointer position/clicks at ~120 Hz on the host clock, and re-render a smoothed cursor plus auto-zoom in a Metal compositor shared between preview and export. Permissions are the main UX hazard: Screen Recording approval needs an app relaunch, macOS 15+ re-prompts monthly ("Allow for one month") unless you use SCContentSharingPicker or hold the VNC-only persistent-content-capture entitlement, listen-only event taps need Input Monitoring (Accessibility for keystroke monitors/active taps), and camera/mic need usage strings plus hardened-runtime entitlements. For export, AVAssetWriter with VideoToolbox hardware encoders is the path; Apple publishes engine counts (M4 Max 2 video + 2 ProRes engines) but no fps, and community numbers (M1 Pro ~52 fps 4K HEVC in ffmpeg; M4 much faster) make 4K60 HEVC plausible but something to benchmark; H.264 via AVAssetWriterInput caps at 4096x2304. GIF should use gifski (AGPL or commercial, C API) rather than ImageIO, whose GIF delay clamps at 100 ms. Pitfalls with primary-source backing: points-vs-pixels scaling, two coordinate systems (Quartz top-left vs AppKit bottom-left), Display P3 default color space, idle frames on static screens (a 10 s recording can become 30 ms unless you re-append frames), minimized windows pause capture, and macOS 26/27 MenuBarExtra behavior changes. Sparkle 2.10.x (Oct 2026) and notarytool are straightforward; no Tahoe-specific notarization rule changes were found.

### xplat-stack

The strongest signal in this sweep is what the two best-known open-source recorders did in 2026: Cap (24k stars, Tauri v2 + SolidJS since 2023) tried an Electron port in August 2026 (PR #2119, closed), then shipped a native Rust GPUI client as opt-in on 15 Sep 2026 and made it "the only Cap desktop app" on 20 Oct 2026, citing speed, battery life and recording reliability; its same-machine benchmark put editor playback at 17.5% CPU / 440 MiB for GPUI versus 76.6% / 3,724 MiB for Tauri and 53.2% / 1,035 MiB for Electron. Meanwhile Screen Studio itself, the product the team wants parity with, is an Electron app (TypeScript, Pixi.js/WebGL renderer, Swift for "some core parts", three-person team, macOS-only), and OpenScreen (5.8k stars, MIT) is Electron + a Rust compositor loaded as an N-API addon with native ScreenCaptureKit/WGC/PipeWire capture. So the realistic pattern for every stack is the same: a Rust (or Swift) native layer owns capture, cursor tracking, GPU compositing and encoding, and the UI shell is a secondary choice; what differs is how much the shell gets in the way. For Tauri the capture/encode crates are usable but young (scap's crates.io release is stale at 0.1.0-beta.1 from Aug 2025 and Cap uses its own in-tree scap-* crates; windows-capture 2.0.1 and xcap 0.9.8 are active; rdev is dead since 2023, and nothing gives Wayland mouse events without evdev), there is no shared-texture path into WKWebView/WebView2/WebKitGTK so preview frames must be copied (Cap used an axum WebSocket pushing raw RGBA/NV12), and the webview itself is the pain: WKWebView features track the user's macOS version (WebGPU only from Safari 26 / macOS 26), WebKitGTK has documented NVIDIA/DMABUF blank-window and stutter issues, and Cap's stated reason for leaving was "bug reports caused by differences between the browser versions available across OS releases". For Electron the blockers are that Chromium bakes the cursor into getDisplayMedia frames (prefer_cursor_embedded(true), the spec's cursor:'never' constraint is unimplemented, Electron's setSkipCursor PR was rejected), so Screen-Studio-style cursor re-rendering requires a native capture addon anyway; the upside is a stable Chromium with WebGPU, WebCodecs and mediabunny (1.65.0, 30 Oct 2026) at the cost of 300–400 MB bundles (Screen Studio installs at 0.6–1.2 GB). Flutter, Qt and .NET MAUI have no credible desktop recording layer (Flutter has only 0.0.1-grade packages; Qt's QScreenCapture is FFmpeg-backend-only with experimental Wayland and no cursor control; MAUI's plugin lacks Windows), so they are not contenders. Given the team's goals, the decision is really between Tauri+Rust (small, fast, but budget for webview quirks and a frame-copy preview) and Electron+Rust-addon (Screen Studio's and OpenScreen's proven path, larger and slower in Cap's numbers), with GPUI as the higher-ceiling, higher-risk native option Cap just validated.

### algorithms

Every credible open-source implementation of Screen-Studio-style effects (Cap in Rust/wgpu, Reframed in Swift, followcursor in Python) uses the same architecture: capture the screen with the OS cursor hidden (ScreenCaptureKit showsCursor=false / WGC IsCursorCaptureEnabled=false), log cursor position, clicks, cursor-shape and keystrokes as a separate metadata stream (60–125 Hz), and re-synthesize cursor, zoom, blur and chrome at edit/export time on a deterministic, precomputed timeline so preview and export are bit-identical. Cursor smoothing in practice is a spring-mass-damper, not Catmull-Rom or Kalman: Cap solves it analytically per 16.7 ms step (crates/rendering/src/spring_mass_damper.rs) with phase-lead compensation (target sampled friction/tension seconds ahead so the smoothed cursor does not lag the video), click anticipation (target snaps to the click point 500 ms early, stiffer "snappy" spring 175 ms before the click), a shake filter and 60 fps decimation; Reframed integrates the same ODE with 1 ms Euler substeps and stiffens it during zoom and typing bursts. Auto-zoom is two layers everywhere: (1) segment generation from clicks (Cap: click −300 ms/+2500 ms, merge gaps ≤2.5 s, default 2.0x; Reframed: dwell gap 0.5 s, hold ≥0.5 s, 0.4 s transitions; followcursor: 3 s click windows, 4 s min gap, chains of ≤4 pans) and (2) a camera that follows a dead-zone box (Cap: all cursor moves greedily clustered into boxes ≤50%x70% of the zoomed viewport, edge-snap ratio 0.25, viewport mathematically clamped inside the frame, center pre-aimed while zoom≈1, springs retargeted every 8 ms instead of eased durations). Motion blur is a single analytic velocity per layer, not frame accumulation: Cap's cursor and pan blur is a 21-tap directional box whose length equals per-frame travel times the user amount (fps-normalized, output fully blurred, no crossfade), and zoom blur is a 13-tap radial kernel with parabolic weights and per-pixel noise dither; Reframed stamps up to 10 offset copies on the CPU. Chrome (padding, rounded/squircle corners, shadow) is one WGSL fragment pass over a signed-distance rounded rect with 4x sub-pixel coverage and a smoothstep shadow; background blur is a separable Gaussian with sigma = 2.5% of frame height. Silence removal is not in Cap or Reframed at all; the strongest building blocks are Silero VAD v6.2.x (512-sample 32 ms windows at 16 kHz, threshold 0.5, min_silence 100 ms, pad 30 ms, <1 ms/chunk) versus WebRTC VAD (10/20/30 ms frames, aggressiveness 0–3), auto-editor (peak-based 4% threshold with 0.2 s margin), and erm for filler words (faster-whisper word timestamps with verbatim prompt, cuts snapped to RMS minima/zero crossings); Screen Studio only added filler/pause removal in 4.0 (Oct 2026). A/V sync in Cap is a hard-won set of mechanisms worth copying: a common mach/QPC time base, rebasing device audio clocks >5 s off, snapping stream start times together when they differ by >30 ms, a frame-cadence gate for high-refresh monitors (decimate when source is >12% fast), last-frame repeat after 3 missed intervals, on-load repair of wrongly stamped tracks, and a flash/click clapperboard tool that reports drift in ms/min. GIF quality comes from gifski (cross-frame palettes plus temporal dithering, quality 90 default in Cap; AGPL-3 with commercial option) or ffmpeg palettegen/paletteuse (sierra2_4a default; bayer or none for flat UI; diff_mode=rectangle for static screens).

### devrel-needs

The 2025-26 market has converged on the Screen Studio feature set (click-driven auto-zoom, cursor smoothing, backgrounds, camera bubble, on-device Whisper captions, aspect-ratio presets), and that set is now commoditized: Screen Studio itself went subscription-only (Oct 2025, Mac-only, no Windows plans), Cap shipped ~20 editor features in 2026 under AGPLv3, and a wave of MIT/AGPL clones (OpenScreen 40k stars then archived, Recordly 36k, Reframed, Screenize) plus a dozen Show HN projects appeared. ### oss

For a company-sponsored, possibly open-sourced Screen-Studio-style recorder, the cleanest path is Apache-2.0 (explicit patent grant and trademark clause, reassuring to corporate adopters; Google formally bans AGPL code internally) with DCO sign-off, a Contributor Covenant 3.0 code of conduct, and a short GOVERNANCE/MAINTAINERS file; a CLA is only worth its friction if you want to keep a relicensing or dual-license option open. Cap (the obvious reference project, ~24k stars) is AGPLv3 except for its MIT `scap-*` and `cap-camera*` capture crates, and its distributed binaries additionally require a commercial license for commercial use, so Cap's app code cannot be copied into a permissive project, while its MIT `scap` crate (ScreenCaptureKit/WGC/PipeWire) can. The 2026 chardet LGPL-to-MIT dispute is the current reference point for clean-room practice: counsel (Meeker, Reed Smith) say a defensible clean room separates people who read the original (spec writers) from implementers who never saw it and keeps contemporaneous documentation; Fontana's view that there is no infringement without identifiable copied expression is "probably right" legally, but reusing names/APIs invited the fight. On codecs, use Apple's VideoToolbox for H.264/HEVC (no GPL, no shipped encoder; Via LA's AVC schedule charges $0 for the first 100,000 units/year but Apple's written position on third-party VideoToolbox use could not be found), keep any FFmpeg build LGPL (no `--enable-gpl`/x264/x265), avoid gifski (AGPL) and gifsicle (GPLv2) in favor of FFmpeg palettegen, and treat AV1 (SVT-AV1 is BSD-3-Clause-Clear plus the AOM royalty-free patent license) as an optional preset because Apple silicon has no hardware AV1 encoder and Safari only plays AV1 on M3+. For macOS, Screen Recording is TCC consent with no entitlement (`com.apple.security.screen-capture` is fake and the App Store rejects it); you need `NSScreenCaptureUsageDescription`, Hardened Runtime, camera and audio-input entitlements, Developer ID signing, a secure timestamp and notarization, and you should design around Sequoia's monthly re-consent prompt (the `persistent-content-capture` entitlement is VNC-only). Distribution via notarized DMG plus Sparkle 2 (EdDSA, sandbox-capable) or the Tauri v2 updater (mandatory minisign-style signatures) and a Homebrew cask (needs 75 stars/30 forks/30 watchers, repo 30+ days old, `zap` stanza) is straightforward; a Mac App Store build is feasible (Recorder.app, a ScreenCaptureKit recorder, shipped there in March 2025) but must be sandboxed, cannot self-update, and must use CGEventTap/Input Monitoring rather than Accessibility for click/keystroke effects. Run a trademark clearance (USPTO Trademark Search replaced TESS in Nov 2023; WIPO Global Brand Database; EUIPO TMview) and document EU use if you register there, since Deepkit lost its EU mark in 2025 for lack of provable genuine use. Precedents: Charm's VHS (MIT) is the model of a devrel tool that thrived; Wulkano's Kap stagnated after 2022; OpenScreen's creator archived it and a community continuation took over; Fig was acquired and shut down; Atom's sunset shows signing-certificate revocation can brick a desktop app, so plan the exit before launch.
