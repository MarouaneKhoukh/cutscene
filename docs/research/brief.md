# Building a Screen Studio–class recorder for DevRel — engineering brief (revision 2)

**Date:** 2026-11-02 · **Audience:** the engineer(s) who will build it · **Scope:** what to build, on what stack, in what order, and what is still unknown.

**How to read this.** This brief synthesizes seven research reports, an adversarial verification pass, and three follow-up investigations (source codec/GOP and editor decoding; ScreenCaptureKit consent paths for area capture; Descript's retake and audio tooling plus loudness standards). Where the verifier corrected a claim, the corrected value is used and marked *(corrected)*. Claims that could not be confirmed are marked *(unverified)* or moved to §8. Two reports (the Screen Studio product survey and the DevRel-needs survey) were not re-verified; their load-bearing claims carry *[not re-verified]*. §5 is a "dirty-team" specification: implementers who have not read Cap's AGPL source should work from §5 and the MIT/Apache references, not from Cap's code (see §6).

**What changed since the previous draft.** (1) The system picker cannot express an area selection, so the consent story in §4.1, §5.1 and §8 is rewritten. (2) A new §5.2 specifies the source recording format (long-GOP, fragmented, no B-frames) and the editor decoder, replacing a one-line "fragmented MP4" note. (3) Descript has shipped retake removal since at least Dec 2023, so §3 row 1 is corrected and Descript's documented failure modes become design rules; new §5.16 (voice enhancement and loudness) and §5.17 (multi-take stitching) are added. (4) The "40 GB project" complaint is downgraded to a single unverified review.

## 0. Decision summary

1. **Build Option A — a macOS-native Swift app** (ScreenCaptureKit → cursor-hidden frames + 120 Hz input telemetry → one Metal compositor shared by preview and export → VideoToolbox), **with a portable engine boundary**: a JSON event log, a JSON project format, and an effects engine (springs, zoom planner, timeline sampler) kept free of UI/OS dependencies and covered by golden test vectors, so it can be ported to Rust/wgpu if Windows/Linux is ever funded. Rationale in §4.5.
2. **Do not clone the commodity feature set and stop.** The 2025–26 clone wave (OpenScreen 40k stars then archived; Recordly 36k; a dozen $19–$199 pay-once apps) has made click-zoom + smoothed cursor + wallpapers table stakes. The DevRel-specific wedge is: multi-take stitching with take-level retake detection, on-device secret redaction, terminal/IDE-aware zoom, keystroke re-timing, command callouts from shell integration, one-recording-to-many-formats, versioned brand kits, on-device audio cleanup, and an agent-drivable CLI/MCP (§3).
3. **License Apache-2.0, sign-off with DCO, keep Cap (AGPL) as spec-only reference, ship notarized DMG + Sparkle + Homebrew cask** (§6).
4. **Minimum macOS 15 (Sequoia)** for v1: it brings SCK microphone capture and HDR, keeps two OS versions of support (15, 26, 27), and lets you write the export path against `AVAssetWriterInput.PixelBufferReceiver` (26+) with the adaptor only as the 15.x fallback *(corrected: the adaptor is deprecated at 27.0)*.
5. **Consent path.** `SCContentSharingPicker` offers exactly five modes (single/multiple windows, single/multiple applications, single display) and `SCContentSharingPickerConfiguration` has no rectangle field ([mode enum](https://developer.apple.com/tutorials/data/documentation/screencapturekit/sccontentsharingpickermode.json), [configuration](https://developer.apple.com/tutorials/data/documentation/screencapturekit/sccontentsharingpickerconfiguration-swift.struct.json)), so area capture must use an app-built `SCContentFilter(display:…)` plus `SCStreamConfiguration.sourceRect` — the non-picker path that needs the one-time Screen Recording TCC grant (plus relaunch) and triggers the macOS 15+ periodic "bypass the system private window picker" alert ([DTS, forum 765103](https://developer.apple.com/forums/thread/765103)). Screen Studio, Cap 0.6.2 and Reframed all use that path and none uses the picker. v1 does the same; the three permission tests in §8 decide whether the picker is adopted for display/window.
6. **Source format.** Record long-GOP hardware HEVC (H.264 fallback) with keyframes every 0.5–1 s set by **both** the frame-count and duration keys, no B-frames, fragmented, roughly 40–120 Mb/s at 4K; decode in the editor through a keyframe index + frame cache + reader pool (§5.2). Not intra-only (ProRes 422 at 4K60 is 530 GB/h) and not FFmpeg's 12-frame default GOP.
7. **Audio.** On-device Studio Sound (vendored xiph/rnnoise, BSD-3) and loudness normalization to −16 LUFS / −1 dBTP in v1, applied non-destructively at preview/export; DeepFilterNet as a v2 quality option (§5.16).

## 2. Top pain points users have today (with evidence)

Ranked by recurrence across Screen Studio's hub, HN, X, Descript's feedback board and reviews *[product survey not re-verified; items marked ✔ were corroborated elsewhere]*:

1. **Price and the subscription model** ✔ — $29/mo monthly, one-time license removed 30 Sep 2025; ≥12 distinct HN commenters and ≥6 X posts in 2025–26; the founder called the $229 tier "a mistake" ([founder post](https://x.com/pie6k/status/1973321084641358308), [HN thread](https://news.ycombinator.com/item?id=47595695), [AlternativeTo](https://alternativeto.net/news/2025/10/screen-studio-has-removed-their-non-subscription-licensing-options-for-new-customers/)). This is the stated trigger for the 2026 clone wave.
2. **Export failures, stuck exports, export time** — "export stuck at 95%" fixed three separate times in 2025 (3.2.2, 3.2.4, 3.4.4), decode failures fixed again in 4.0.2 and 4.1.0; hub post ["Export is failed"](https://hub.screen.studio/p/export-is-failed) (7–20 Oct 2026: "couldn't finish creating the final sound file", 4K Studio exports fail while HD works) had no staff reply; an 8.43 GB RAM spike exporting one minute of 4K (X, 6 Oct 2026) *[not re-verified]*. Cap's open export bugs are decoder-reliability problems, not codec problems ✔: stale/flickering frames on macOS only, same bundle exports correctly on Windows ([#1787](https://github.com/CapSoftware/Cap/issues/1787)); export stuck on the last frame ([#1940](https://github.com/CapSoftware/Cap/issues/1940)); `AVAssetReader` failing mid-stream with −11821 "Cannot Decode" when many decode sessions run at once, previously answered with stale cached frames ([PR #2872](https://github.com/CapSoftware/Cap/pull/2872)).
3. **Crashes and regressions around 4.0** — Intel/AMD-GPU black editor confirmed by a team member ([X](https://x.com/merlindru/status/2108952792966607043)), removed mic modes ([hub](https://hub.screen.studio/p/where-is-microphone-audio-mode)), camera-layout settings collapsed to one value, forced background blur during zooms.
4. **Missing editing primitives (largest by votes)** — import/append clips 534 votes (open since Oct 2023), text slides 482, multi-clip 467 (in progress), voice-over 343, import audio 324, enter/exit animations 312, annotations 248 ([hub roadmap](https://hub.screen.studio/roadmap)). First-hand: a creator still exports to ScreenFlow because Screen Studio "cannot merge recorded sequences" ([numericcitizen, 28 Sep 2025](https://meta.numericcitizen.me/2025/09/28/screenflow-screen-studio.html)).
5. **Auto-zoom picks the wrong target and offers no control** ✔ — zooms "often start and end too late" ([hub, 18 Aug 2025](https://hub.screen.studio/p/custom-settings-for-default-automatic-zoom-range)); "too aggressive" cursor following with requests for range, follow delay/speed and pointer offset ([hub, 27 Oct 2026](https://hub.screen.studio/p/advanced-auto-zoom-adjustments)); panning "very distracting and almost dizzying" ([HN](https://news.ycombinator.com/item?id=47595695)); Cap users report over-merged zooms ([#2928](https://github.com/CapSoftware/Cap/issues/2928)). Because every tool triggers on clicks, typing-heavy terminal/IDE work gets no zoom at all.
6. **Disk, memory and bundle bloat** — the "40 GB project for a 3-hour recording" figure comes from one Product Hunt review in the unverified product survey and could not be found on hub.screen.studio's first page or changelog *[not re-verified; see §8]*; what is verifiable is the code: Cap's default macOS Studio path writes 34–54 GB/h at 4K (Balanced) and up to 179 GB/h (Ultra) ([capture_pipeline.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/recording/src/capture_pipeline.rs)), a Cap user reports a 40-minute recording over 2 GB that is "choppy and laggy" in editor and export ([#2144](https://github.com/CapSoftware/Cap/issues/2144)), Screen Studio's bundle is 1.17 GB, and the 2023 auto-updater incident (250 MB re-downloaded every 5 minutes, ~$8,000 bill) resurfaced on HN in Apr 2025 with heavy anti-Electron sentiment ([HN](https://news.ycombinator.com/item?id=43829006)).
7. **Mac-only** ✔ — "Waiting for Windows version" 302 votes, Rejected ([hub](https://hub.screen.studio/p/waiting-for-windows-version)); this gap spawned FocuSee, Recordly, OpenScreen, Cap's Windows/Linux builds.
8. **Thin audio editing, share-link limits, masking limits** — one mask layer at a time, masks don't follow scrolling, fade-in briefly reveals content ([hub](https://hub.screen.studio/p/multiple-mask-layers)); logo watermark requested (93 votes); 30-minute share cap.
9. **Cursor smoothing desynchronizes pointer from UI** — hover states appear before the smoothed cursor arrives (hub, 14 Oct 2026) — the reason Screen Studio recommends disabling smoothing on dropdown fragments ([guide](https://screen.studio/guide/disable-smooth-mouse-movement)).
10. **A/V sync and timestamping is the dominant engineering problem in the field** ✔ — every Cap release Jan–Oct 2026 carries a timing fix; the cursor-drift bug ([#2144](https://github.com/CapSoftware/Cap/issues/2144)) is still open with a contributor diagnosis (frames re-stamped with dequeue time, 100–300 ms late when the encoder falls behind on 120/144 Hz Retina displays) and a linked open PR #2315; Cap's `mp4.rs` history shows repeated PTS-monotonicity and pause-timing fixes May–Aug 2026, i.e. `AVAssetWriter` timestamp handling under pause/VFR caused more bugs than codec settings ([PR #1732 context](https://github.com/CapSoftware/Cap/pull/1732)). Storage matters too: a 38-minute near-4K recording to an SD card lost ~10% of video in 16 gaps with 22–25 s process freezes ([#2366](https://github.com/CapSoftware/Cap/issues/2366)).
11. **Distribution friction in the OSS field** ✔ — ScreenCraft, OpenScreenStudio, Screenize, Vuoom and the original OpenScreen all ship unsigned/un-notarized builds; OpenScreen only got Developer-ID signing in 1.9.0 and warns that permission grants from unsigned builds don't carry over.
12. **DevRel-specific cost: retakes and assembly** *[not re-verified]* — Stripe measured ~20 hours per pre-recorded tutorial before restructuring production ([DevRelCon 2021](https://developerrelations.com/talks/stripe-multiplexed-video-production)); the three-tool workflow (Screen Studio → ScreenFlow → Whisper CLI) is the status quo to collapse.
13. **Automated cleanup that edits without review** ✔ (new) — Descript's Remove Retakes "tends to re-construct sentences using multiple takes … when one sentence has 3–4 cuts, it sounds really choppy" ([feedback, 2 Dec 2025](https://feedback.descript.com/feature-requests/p/use-one-retake-instead-of-multiple-cuts-1)); it misses takes and trims the final take ([thread, Oct–Dec 2023](https://feedback.descript.com/feature-requests/p/auto-detect-multiple-takes-game-changer)); it has no next/prev review navigation, which makes it "almost impossible to use on long podcasts" ([feedback, Aug–Sep 2024](https://feedback.descript.com/feature-requests/p/remove-retakes-needs-next-prev-to-preview-before-committing-the-change)); transcription itself degrades on repeated takes ([feedback, 9 May 2025](https://feedback.descript.com/feature-requests/p/retake-markup-button-or-voice-for-better-retake-text-recognition-transcription)); Trustpilot (2.6/5, 292 reviews) has Aug and Oct 2026 reviewers reporting filler/pause removal "deleting actual words" and desyncing audio ([Trustpilot](https://www.trustpilot.com/review/descript.com), unmoderated). Design rule: every automated edit gets a review list with preview and accept/reject before it is applied.
14. **Emerging: agent control** — hub ["MCP Please!"](https://hub.screen.studio/p/mcp-please) (13 Oct 2026), X users wanting Claude/Devin to drive recording; Cap, OpenScreen, Tella and Descript already expose MCP/CLI.

## 4. Architecture options

All three options share the same core design, which every serious implementation surveyed converged on (Cap, Reframed, Screenize, ScreenCraft, Vuoom, OpenScreen 2.x): **capture the screen with the OS cursor hidden, log pointer/click/cursor-shape/keystroke events as a separate 60–125 Hz stream on the host clock, write a long-GOP fragmented source file, and re-synthesize cursor, zoom, blur and chrome at edit/export time from a deterministic precomputed timeline so preview and export are identical.** The options differ in who owns the UI shell and how frames reach the preview. The macOS consent problem (§4.1) is architecture-neutral: Chromium's and Electron's `useSystemPicker` also expose only display/window, so area capture is a non-picker stream on every stack.

### 4.1 Option A — macOS-only native Swift

**Concrete stack.** Swift + SwiftUI/AppKit (menu-bar app via `NSStatusItem` + `NSPopover`, not `MenuBarExtra`, which has no public show/hide API and whose window-style internals changed again in macOS 27 — see [MenuBarExtraAccess PR #26](https://github.com/orchetect/MenuBarExtraAccess/pull/26)); `SCStream` for display/window/area capture with `showsCursor = false`; selection UI = our own overlay window (as Screen Studio's "recording picker", Reframed and Cap do) with `SCContentFilter(display:excludingApplications:exceptingWindows:)` + `sourceRect` for area, `SCContentFilter(desktopIndependentWindow:)` for windows, and the system `SCContentSharingPicker` for display/window only behind a flag until the §8 tests pass; system audio via SCK (`capturesAudio`, 13.0+) or Core Audio process taps (14.2+); microphone via SCK (`SCStreamOutputType.microphone`, 15.0+) or `AVCaptureSession`; camera via `AVCaptureSession` (`continuityCamera` device type, 14.0+; `AVCaptureMultiCamSession` does not exist on macOS); telemetry via `CGEvent(source:nil).location` polling at 120 Hz plus a listen-only `CGEventTap` for clicks/keys (Input Monitoring) and cursor-shape hashing from `NSCursor.currentSystem`; encoding via `VTCompressionSession` (or `AVAssetWriter` compression settings) into a fragmented `AVAssetWriter` file (§5.2); one Metal compositor (MSL) used for both the editor preview and the offline export; `AVAssetWriter` + VideoToolbox hardware encoders (H.264/HEVC/ProRes/HEVC-with-alpha), `kVTCompressionPropertyKey_RealTime = false` for export; captions via WhisperKit (as Reframed) or Apple Speech; RNNoise (C, BSD-3) for voice enhancement; GIF via FFmpeg palette path or gifski behind a process boundary; Sparkle 2.10.x updater; notarytool; Homebrew cask.

**Quality ceiling.** The highest of the three on Mac: IOSurface-backed SCK frames go straight to Metal and to the hardware encoder with no copies; Cap's own measurement of a native editor vs a webview editor on the same media stack is 17.5% CPU / 440 MiB vs 76.6% / 3,724 MiB (Tauri) and 53.2% / 1,035 MiB (Electron) ([PR #2133](https://github.com/CapSoftware/Cap/pull/2133), [deep dive](https://cap.so/blog/rebuilding-cap-in-gpui)); a Swift app bundle is tens of MB vs Screen Studio's 1,167 MB. Apple-only extras: `VTFrameProcessor` ML motion blur/frame-rate conversion (15.4+), on-device super-resolution (26+), Vision OCR for redaction, `AVAudioEngine` voice processing for live mic cleanup.

**Effort to Screen Studio parity (architect's estimate, not sourced).** Lowest: capture, encode, camera, speech and OCR are OS-provided; the work is the effects engine, timeline, editor decoder and editor UX. Anchors: Screenize went from first commit (21 Jan 2026) to v0.4.3 with two auto-zoom modes, keystroke overlay and 4K/240 fps export by 28 Mar 2026 (one developer); Reframed reached most Screen Studio effects plus captions by its 0.14.x releases (Mar–Apr 2026, one developer). A usable v1 (§7) is a one-to-two-engineer, roughly one-quarter effort with agentic assistance; full parity minus cloud features is a multi-quarter effort (Screen Studio is a 3–5 person team four years in).

**Risks.** Mac-only (complaint #7; limits the open-source community — the 30k+-star projects are all cross-platform). Swift-only effects code is not portable, hence the portable-engine discipline. **TCC UX:** the non-picker path is a consent path of its own — `SCShareableContent` needs the Screen Recording grant and Apple's sample says the first run prompts and requires a restart ([sample](https://developer.apple.com/tutorials/data/documentation/screencapturekit/capturing-screen-content-in-macos.json)); DTS confirmed that pure-SCK non-picker capture shows the "bypass the system private window picker" alert (on the second use) and named only the VNC-only `persistent-content-capture` entitlement and the picker as ways to avoid it ([forum 765103](https://developer.apple.com/forums/thread/765103)); DTS in Oct 2026 called the TCC grant and the picker "the two documented ways for the person to give consent" ([forum 849969](https://developer.apple.com/forums/thread/849969)). The alert still ships on macOS 26.7 (ReplayKit's loctable carries the title, body, "Allow" and "Open System Settings" strings — the 2024 "Allow For One Month" wording is gone; read from the local SDK, no URL) and `replayd` tracks approvals per bundle ID with last-used/last-alerted dates, so a recorder that offers area capture is an "alerting" app regardless of how its other modes behave. Apple has never published the interval (weekly → monthly in Sequoia beta 6, 14 Aug 2024 → usage-based "fewer dialogs" in 15.1; [timeline](https://mjtsai.com/blog/2024/08/08/sequoia-screen-recording-prompts-and-the-persistent-content-capture-entitlement/)). macOS 27 adds a separate "Remote Desktop" TCC category with no API to query it ([forum 841530](https://developer.apple.com/forums/thread/841530)) and its beta 4 makes `CGWindowListCreateImage` return a gray image ([forum 849969](https://developer.apple.com/forums/thread/849969)) — use no CG capture API anywhere. `NSCursor.currentSystem` is deprecated in macOS 27 and its deprecation message points only to SCK `showsCursor` or `NSCursor.currentCursor`, i.e. there is no replacement for reading another app's cursor image *(corrected; [doc](https://developer.apple.com/documentation/appkit/nscursor/currentsystem))*. Event taps can be silently disabled after re-signing ([TIL, Feb 2026](https://danielraffel.me/til/2026/02/19/cgevent-taps-and-code-signing-the-silent-disable-race/)). App Sandbox blocks Accessibility, so a Mac App Store build would need `CGEventTap`/Input Monitoring and would lose Sparkle ([forum 789896](https://developer.apple.com/forums/thread/789896), [App Review 2.4.5](https://developer.apple.com/app-store/review/guidelines/)). gifski is AGPL. Unanswered forum reports of capture stopping silently after 10–15 min ([822439](https://developer.apple.com/forums/thread/822439)) and overlays missing from captures ([761155](https://developer.apple.com/forums/thread/761155)). Editor decoding at 4K is the least-measured part of the stack (§5.2, §8).

**Verified API notes (minimum versions).**
- ScreenCaptureKit framework 12.3+: `SCStream`, `SCContentFilter` (display / display−windows / display+apps / single window), `showsCursor`, `pixelFormat` ∈ {BGRA, l10r, 420v, 420f}, `queueDepth` 3–8 (release frames within `minimumFrameInterval × (queueDepth−1)`), `colorSpaceName` defaults to the display's space (Display P3) — pin sRGB or tag the file ([docs](https://developer.apple.com/documentation/screencapturekit)).
- `SCStreamConfiguration.sourceRect` is "specified in points in the display's logical coordinate system"; the web doc says it is ignored for single-window capture while the 26.2 SDK header mentions independent-window streams — treat window+sourceRect as unreliable; Reframed and Cap crop display streams only ([doc](https://developer.apple.com/tutorials/data/documentation/screencapturekit/scstreamconfiguration/sourcerect.json)).
- `SCContentSharingPicker` 14.0+ ("Avoid creating your own sharing picker"): modes singleWindow, multipleWindows, singleApplication, multipleApplications, singleDisplay — no region mode in the 26.2 SDK; configuration knobs are allowedPickerModes, excludedWindowIDs, excludedBundleIDs, allowsChangingSelectedContent (camera/mic controls are iOS 27-only); `SCContentFilter.contentRect`/`pointPixelScale` (14.0+) let you map an overlay rectangle into a picker filter's coordinates ([filter doc](https://developer.apple.com/tutorials/data/documentation/screencapturekit/sccontentfilter.json)). Chromium documents that an `SCStream` fed a picker-originated filter captures "without global permissions" while `SCScreenshotManager` always enforces TCC ([native_screen_capture_picker_mac.mm](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/media/capture/native_screen_capture_picker_mac.mm)); Electron exposes this as `useSystemPicker`, "experimental … MacOS 15+ only".
- Consent mechanics: `getCurrentProcessShareableContent` (14.4+) is the only consent-free query; `CGPreflightScreenCaptureAccess()` never adds the app to the Screen Recording list — call `CGRequestScreenCaptureAccess()` at startup; ad-hoc signing resets the TCC identity on every build (forum threads 819525/819406, Mar 2026). TCC service names on 26.7: ScreenCapture, ListenEvent, PostEvent, Accessibility, AudioCapture, Camera, Microphone, RemoteDesktop (`tccutil reset ScreenCapture`). MDM Restrictions key `forceBypassScreenCaptureAlert` (15.1+) removes the alert on managed Macs only ([Restrictions](https://developer.apple.com/documentation/devicemanagement/restrictions)). Apple's own macOS 15 release note blames deprecated CG APIs and says to migrate to "ScreenCaptureKit and SCContentSharingPicker" ([notes](https://developer.apple.com/tutorials/data/documentation/macos-release-notes/macos-15-release-notes.json)), but the DTS threads show pure-SCK non-picker capture alerts too. The `persistent-content-capture` entitlement is VNC-only and form-gated ([doc](https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.developer.persistent-content-capture.json)).
- Frame delivery is change-driven and capped at min(requested, native): a static screen yields idle frames and a naive writer produces a 30 ms file for a 10 s recording — re-append the last frame ([Nonstrict](https://nonstrict.eu/blog/2023/recording-to-disk-with-screencapturekit/)); attachments include status, displayTime, scaleFactor, contentScale, contentRect, dirtyRects, videoOrientation. Reframed requests `minimumFrameInterval` at fps × 1.2 with `queueDepth` 8; Apple's sample uses 5 at 60 fps.
- System audio `capturesAudio` 13.0+ (48 kHz default; single-window filter captures the whole app's audio); `SCStream.synchronizationClock` 13.0+ (sync with `AVCaptureSession.synchronizationClock`, 12.3+) ([doc](https://developer.apple.com/documentation/screencapturekit/scstream/synchronizationclock)).
- `includeMenuBar` 14.2+; `SCScreenshotManager` 14.0+, `captureImage(in: CGRect)` 15.2+, `captureScreenshot(rect:configuration:)` 26.0+ — stills only and TCC-enforced; Core Audio process taps 14.2+ with `NSAudioCaptureUsageDescription` and a separate permission prompt ([sample](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)).
- 15.0+: `SCStreamOutputType.microphone`, `showMouseClicks` (BGRA only), HDR via `captureDynamicRange`/presets (≥10-bit + HLG/PQ), `SCRecordingOutput` — exposes only outputURL/outputFileType/videoCodecType with **no bitrate, GOP or quality control** (verified against the SDK header), so use SCStream + your own writer.
- 26.0+: `SCScreenshotConfiguration`, preset `captureHDRRecordingPreservedSDRHDR10` *(corrected: 26, not 27)*, `AVAssetWriterInput.PixelBufferReceiver` (`append(_:with:)` async / `appendImmediately`), `AVVideoCodecType.proResRAW`. 27.0+: `SCClipBufferingOutput`, `SCRecordingEditor`, `mixesAudioWithMicrophone`; `AVAssetWriterInputPixelBufferAdaptor` and `expectsMediaDataInRealTime` deprecated *(corrected)*.
- VideoToolbox keyframe control: `kVTCompressionPropertyKey_MaxKeyFrameInterval` defaults to 0, "which indicates that the video encoder should choose where to place all key frames"; `kVTCompressionPropertyKey_MaxKeyFrameIntervalDuration` is "zero by default, which means no limit … particularly useful when the frame rate is variable"; both may be set together ("a keyframe every X frames or every Y seconds, whichever comes first") ([doc](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_maxkeyframeinterval); header text from the macOS 26 SDK). `AVVideoAllowFrameReorderingKey` defaults to YES; NO "may yield the best results" for real-time sources. `AVVideoSettings.h` labels `AVVideoMaxKeyFrameIntervalKey`, `AVVideoMaxKeyFrameIntervalDurationKey` and `AVVideoAverageBitRateKey` "(H.264 only)" — whether `AVAssetWriter` honours them for HEVC is unverified (§8); driving `VTCompressionSession` directly avoids the question.
- Permissions: `CGPreflightScreenCaptureAccess`/`CGRequestScreenCaptureAccess` 10.15+; `CGPreflightListenEventAccess`/`CGRequestListenEventAccess` 10.15+; `CGEvent.tapCreate` keyboard events require root or assistive access; `.listenOnly` taps prompt Input Monitoring and `.defaultTap` prompts Accessibility (community reports, 2019–21); `NSEvent.addGlobalMonitorForEvents` key events need `AXIsProcessTrusted`.
- Usage strings: `NSCameraUsageDescription`/`NSMicrophoneUsageDescription` mandatory (missing key terminates the app); `NSScreenCaptureUsageDescription` recommended by the framework overview though tccd on 26.7 does not list it; entitlements `com.apple.security.device.camera` and `.audio-input`; there is **no** screen-capture entitlement (`com.apple.security.screen-capture` is bogus and App Store ingestion rejects it, [forum 778616](https://developer.apple.com/forums/thread/778616)).
- Camera: `reactionEffectsEnabled` is on by default for all macOS apps and `reactionEffectGesturesEnabled` (14.0+) is **read-only** — you cannot suppress gesture-triggered confetti; tell users to disable Gestures in Control Center *(corrected; [doc](https://developer.apple.com/documentation/avfoundation/avcapturedevice/reactioneffectgesturesenabled))*.
- Audio: `AVAudioEngine` voice processing (`setVoiceProcessingEnabled`, macOS 10.15+) gives echo cancellation, noise suppression and AGC (AGC on by default) but requires both I/O nodes in voice-processing mode, can only be toggled while the engine is stopped, is unavailable in manual-rendering mode, and forces matching input/output formats ([doc](https://developer.apple.com/tutorials/data/documentation/avfaudio/avaudioionode/setvoiceprocessingenabled(_:).json)); users of such apps can pick the system "Voice Isolation" microphone mode from Control Center (`AVCaptureDevice.preferredMicrophoneMode`, 12.0+, [doc](https://developer.apple.com/tutorials/data/documentation/avfoundation/avcapturedevice/microphonemode.json)). Live-only and Mac-only, so an optional capture-time stage, not the export stage.
- Export: `AVVideoCodecType.h264/hevc/hevcWithAlpha (10.15+)/proRes422*/proRes4444/JPEGXL (15+)`; `kVTVideoEncoderSpecification_RequireHardwareAcceleratedVideoEncoder` 10.9+ (can fail when hardware is busy); H.264 via `AVAssetWriterInput` crashed above 4096×2304 in a 2023 observation (not re-verified on current OS); Apple publishes engine counts only (M4 Max: 2 video encode + 2 ProRes engines, [specs](https://support.apple.com/en-us/122211)); community numbers put 4K HEVC hardware encode at ~52 fps on M1 Pro and far higher on M4 ([HandBrake #7142](https://github.com/HandBrake/HandBrake/discussions/7142)) — benchmark before promising 4K60 real-time.
- `VTFrameProcessor` 15.4+ (frame-rate conversion, motion blur 1–100, optical flow, temporal noise); `VTSuperResolutionScalerConfiguration` 26.0+ needs a model download ([doc](https://developer.apple.com/documentation/videotoolbox/vtframeprocessor)).
- Sparkle 2.10.1 (25 Oct 2026): EdDSA appcasts, macOS 12+, MIT with BSD-2/zlib components ([releases](https://github.com/sparkle-project/Sparkle/releases)). macOS 27 "Golden Gate" shipped 14 Sep 2026 ([Eclectic Light](https://eclecticlight.co/2026/09/14/apple-has-released-macos-golden-gate-and-security-updates-to-tahoe-26-7-sequoia-15-8/)).
- Permissive Swift references: Reframed (MIT; area capture = CG TCC APIs + `SCShareableContent` + borderless overlay at `.screenSaver` level + display filter with `sourceRect`, [repo](https://github.com/jkuri/reframed)), Screenize (Apache-2.0, paused 22 May 2026, [repo](https://github.com/syi0808/screenize)), Open Recorder (Apache-2.0, Swift + Rust, [repo](https://github.com/imbhargav5/open-recorder)), Apple's macOS 15 sample (queueDepth 5 at 60 fps, excludes own app via bundle ID), Nonstrict's SCK→AVAssetWriter example. QuickRecorder is AGPL (read-only reference). SmoothCursor has **no license file** and should not be reused *(corrected)*.

### 4.2 Option B — Tauri v2 + Rust (cross-platform)

**Concrete stack.** Tauri 2.x shell (WKWebView / WebView2 / WebKitGTK via wry) with a SolidJS/React editor; Rust core: `scap` (MIT, CapSoftware/scap — crates.io is stale at 0.1.0-beta.1 from Aug 2025, depend on git), or per-platform crates: `screencapturekit` 11.1.1 (26 Oct 2026, Swift bridge, macOS 12.3+) + `cidre` 0.29.0 for VideoToolbox on macOS; `windows-capture` 2.0.1 (8 Aug 2026, MIT; WGC + DXGI, built-in encoder on WinRT MediaTranscoder accepting `IDirect3DSurface` zero-copy *(corrected)*) or raw `windows` 0.60 + Media Foundation; `ashpd` 0.13.13 + `pipewire` 0.10 (or `waycap-rs` 3.0.1, MIT, ready PipeWire→VA-API/NVENC pipeline *(corrected version)*) on Linux; `wgpu` 30.0.1 compositor with WGSL; `ffmpeg-next` 9.0.0 (WTFPL bindings, LGPL FFmpeg build) or `ffmpeg-sidecar` 2.7.0; `device_query` 4.0.1 for cursor polling; `whisper-rs` 0.11 / `parakeet-rs` 0.3.4; `cap-rnnoise`-style vendored RNNoise; Tauri updater (mandatory minisign signatures, Rust ≥ 1.90). If you encode through FFmpeg's `h264_videotoolbox`, set `g` explicitly — Cap's realtime branch never did and shipped a 12-frame GOP ([PR #2502](https://github.com/CapSoftware/Cap/pull/2502)).

**Quality ceiling.** Capture and export equal Option A where the Rust core owns them. The editor is bounded by the webview: there is **no shared-texture path into any of the three system webviews**, so preview frames are copied (Cap pushed raw RGBA/NV12 over a local axum WebSocket; 1080p RGBA at 60 fps ≈ 500 MB/s) or a native wgpu surface is layered under a transparent child webview (wry's `examples/wgpu.rs`, which rejects Wayland). WKWebView features track the user's OS (WebGPU confirmed only on macOS 26+; Safari 26.1 also installs on 14/15 — untested *(corrected)*); WebKitGTK has documented NVIDIA/DMABUF blank-window issues whose recommended workaround keeps changing (disabling DMABUF now crashes on current WebKitGTK, [radar PR #646→#1974](https://github.com/skyhook-io/radar/pull/646); Debian has added and dropped its NVIDIA patch repeatedly) *(corrected)*.

**Effort to parity.** Highest: three capture backends, three encoder backends, Wayland input capture (no mouse events without evdev/input group), plus webview workarounds, on three signing pipelines. Cap, a funded company, ran this stack 2023→2026 and then rewrote the UI; its GPUI README still lists unfinished windows and settings pages.

**Risks.** The two most visible Tauri desktop apps in this space both left it in 2026 for the same reason — "bug reports caused by differences between the browser versions available across OS releases" (Cap [PR #2119](https://github.com/CapSoftware/Cap/pull/2119), [PR #3529](https://github.com/CapSoftware/Cap/pull/3529); Codux [#29](https://github.com/duxweb/codux/issues/29), repo since archived). wgpu moves fast (30.x) while Cap pins 25 with a vendored `wgpu-hal` patch and OpenScreen pins 24 (naga 25+ breaks FXC SM 5.0 HLSL). Cap's open Wayland bug ([#2419](https://github.com/CapSoftware/Cap/issues/2419)) and ScreenCraft's X11-only click logging show Linux cursor fidelity is unsolved. Tauri's bundle-size advantage shrinks once encoders ship (Cap: 204 MiB Tauri vs 162 MiB GPUI vs 410 MiB Electron). Tauri 3's CEF runtime (3.0.0-alpha.6, 14 Oct 2026) would fix webview drift at Electron-like size, defeating the point.

### 4.3 Option C — Electron + web

**Concrete stack.** Electron 43 (2 Jul 2026, Chromium 150, Node 24.17; 8-week cadence, only the latest three majors supported *(corrected: Electron 39 is already unsupported)*), React/TypeScript, Pixi.js/WebGL or WebGPU compositor in the renderer (Screen Studio uses Pixi.js with React Pixi Fiber), WebCodecs + `mediabunny` 1.65.0 (MPL-2.0, 30 Oct 2026, Screen Studio is a sponsor) for muxing, **plus a native capture helper per OS regardless** — Chromium composites the cursor into every `getDisplayMedia` frame via `DesktopAndCursorComposer` on all platforms, nothing implements the spec's `cursor: "never"`, and Electron's `setSkipCursor` PR was closed in Mar 2022 *(corrected mechanism; [source](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/media/capture/desktop_capture_device.cc))*; OpenScreen's pattern: Swift SCK helper, C++ WGC helper, Rust PipeWire helper, optional Rust napi compositor; `uiohook-napi` 1.5.5 for global input (libuiohook, LGPL-style, no Wayland); electron-builder + notarization; Squirrel/electron-updater.

**Quality ceiling.** Proven to reach Screen Studio quality (Screen Studio is this stack), at the cost of Cap's measured 53.2% CPU / 1,035 MiB playback, a ≥280 MB installed baseline (Arch `electron39` 39.8.10: 80.5 MB package / 280.3 MB installed *(corrected)*) and 300 MB–1.2 GB real bundles (Better Stack's recorder 323 MB; Screen Studio 1,167 MB). Native-compositor preview into the renderer is CPU readback on macOS/Linux — OpenScreen's shared GPU textures are **Windows-only**, and its macOS canvas preview runs 20–26 fps vs ~57 composed *(corrected; [preview.md](https://raw.githubusercontent.com/getopenscreen/openscreen/main/technical-documentation/architecture/preview.md))*.

**Effort to parity.** Medium: the largest talent pool, stable Chromium everywhere, and OpenScreen (MIT) as a near-complete reference — but reproducing OpenScreen yields no differentiation in a field that already has two 35–40k-star Electron recorders.

**Risks.** Bloat and background-download behavior are a top-six Screen Studio complaint and the HN community's anti-Electron reflex is strong. Electron's macOS system-audio trap (14.2+ CoreAudio tap needs System Audio Recording permission or the track is created ended with no JS error; workaround `--disable-features=MacCatapLoopbackAudioForScreenShare`, [Electron 39 notes](https://www.electronjs.org/blog/electron-39-0)). Kap's decay: last release Oct 2022 on Electron 13.6.9 (EOL Feb 2022) with an unpatched RunAsNode advisory ([commits](https://github.com/wulkano/Kap/commits/main)). Version treadmill. WebGPU on Linux still reported needing flags in late 2025 ([#41763](https://github.com/electron/electron/issues/41763)).

### 4.4 Option D (for completeness) — Rust core + GPUI, Cap's current path

Highest cross-platform ceiling (Cap: 17.5% CPU / 440 MiB; installers down 49% on macOS arm64) but GPUI is a pinned Zed fork with custom patches, hand-built text fields (~2,700 lines), incomplete keyboard navigation, no hot reload, and macOS 26/27 platform shims ([deep dive](https://cap.so/blog/rebuilding-cap-in-gpui)). Too much framework risk for a small team today; the right fallback if cross-platform becomes mandatory later.

### 4.5 Recommendation: Option A, macOS-native Swift, with a portable engine boundary

Rationale:
1. **The product being matched is Mac-only, so parity does not require cross-platform**, and a DevRel team's primary need is a tool that works on their Macs this quarter. Option A has the shortest path to a Screen Studio–quality result because capture, encode, camera, speech and OCR are OS-provided and the only unproven work is the effects engine and editor decoder, for which permissive Swift references exist (Reframed MIT, Screenize Apache-2.0).
2. **Both webview options were abandoned or outperformed by native in 2026.** Cap left Tauri for a native UI citing webview inconsistency, and measured native at 4× less CPU and 8× less memory than its Tauri editor; Screen Studio's Electron app is 1.17 GB and bloat is a top-tier complaint. A native Swift app is the one architecture that can credibly beat Screen Studio on the complaints users actually voice (size, memory, export reliability).
3. **The DevRel differentiators are Mac-richest:** Accessibility caret bounds, Vision OCR for redaction, Apple Speech/WhisperKit captions, HEVC-with-alpha export, `VTFrameProcessor`, `AVAudioEngine` voice processing.
4. **Open-source positioning:** the Electron/Rust cross-platform space is crowded (OpenScreen, Recordly, Cap) and partly AGPL; a polished Apache-2.0 native Mac recorder is underserved (Reframed 169 stars, Screenize paused).
5. **The portable-engine discipline keeps the door open.** Put the cursor spring, zoom planner, re-timing, retake matcher and timeline sampling in a UI-free Swift module with golden test vectors (input event log → expected timeline samples); specify the event log and project file as versioned JSON schemas. A later Rust/wgpu port for Windows/Linux (Option D or a Rust core with per-OS shells) can be validated against those vectors. Do **not** write Swift↔Rust FFI in v1; the engine is small (Cap's equivalents are ~2k lines of cursor code and ~3.4k lines of zoom code) and FFI buys nothing until a second platform is funded.
6. **Consent and codec constraints do not favour any option.** Area capture is a non-picker SCK stream on every stack, the periodic alert is per app, and VideoToolbox is the encoder in all three; Swift simply removes two layers (bindings, FFmpeg defaults) between you and those APIs.

If cross-platform is declared non-negotiable before v1, choose Option D's shape (Rust core + native shells, or Electron + Rust napi only if the team is web-only) — not Tauri.

## 5. Effect implementation notes

Minimum macOS 15; all constants below are design parameters to tune, not code to copy. Cap files are cited as the most complete spec of each behavior (AGPL — read for behavior only, see §6); Reframed/followcursor/KeyCastr are permissively licensed and may be adapted with attribution.

### 5.1 Capture, selection, consent and telemetry foundation
- **Stream.** `SCStream` with `showsCursor = false`, `pixelFormat = BGRA` (or 420v for the encoder path), `queueDepth 5–8`, `minimumFrameInterval = 1/60` (or 1/120 on ProMotion — measure), width/height in **pixels** (`display.width × scaleFactor`, rounded to even), exclude your own app via `excludingApplications` with `Bundle.main.bundleIdentifier` (Apple sample).
- **Area selection** (direct path, as all three shipping references): a borderless overlay `NSWindow` per screen at `.screenSaver` level with `[.canJoinAllSpaces, .fullScreenAuxiliary]` that can become key; convert the drag rect to even-sized, display-local, Quartz top-left coordinates (`localQuartzY = displayHeight − localAppKitY − h`), find the `SCDisplay` by `displayID`, set `sourceRect` in points and `width/height = round(points × scale) & ~1`; offer aspect-ratio presets and typed dimensions (Screen Studio's and Cap 0.5.7's area UX). Test fractional scales — Cap 0.6.2 fixed "area recordings at scales like 175% keep their exact size" ([releases](https://github.com/CapSoftware/Cap/releases)). Reference: Reframed `SelectionOverlayWindow.swift`, `SelectionRect.swift`, `RecordingCoordinator+Screen.swift`, `ScreenCaptureSession.swift` ([repo](https://github.com/jkuri/reframed), MIT).
- **Consent flow.** At first launch call `CGRequestScreenCaptureAccess()` (preflight alone never lists the app), explain that macOS requires a relaunch after the grant, and expect the "bypass the system private window picker" alert on the second direct-path capture; your copy must match the 26.7 strings (title + body, buttons "Allow" / "Open System Settings") and must not promise "no monthly prompt". Keep the picker (`allowedPickerModes = [.singleDisplay, .singleWindow]`) behind a flag; run §8 Tests 1–3 before exposing it, and if the hybrid in Test 2 works (picker-selected display + overlay + `sourceRect` on the picker's filter), area capture can become alert-free at the cost of a system picker click per session.
- **Telemetry.** A 120 Hz `DispatchSourceTimer` (8 ms) reading `NSEvent.mouseLocation` + `NSEvent.pressedMouseButtons` (or `CGEvent(source:nil).location` — note AppKit is bottom-left origin, Quartz top-left; `CGDisplayBounds` is relative to the main display's top-left), a 16 ms cursor-type poll hashing `NSCursor.currentSystem` image bytes (Cap's approach; resolution-independent) with an SVG/PDF sprite table and normalized hotspots (arrow ≈ (0.30, 0.23), I-beam ≈ (0.48, 0.52), pointing hand ≈ (0.34, 0.17)); clicks and keystrokes from a listen-only `CGEventTap`. Stamp everything with `CMClockGetTime(CMClockGetHostTimeClock())` minus pause offsets; normalize positions to the capture rect so they survive cropping. Reference: [Reframed CursorMetadataRecorder.swift](https://raw.githubusercontent.com/jkuri/reframed/main/Reframed/Recording/CursorMetadataRecorder.swift) (MIT; it labels 8 ms as "120 Hz" but consumers interpolate on timestamps, so the label is harmless); Cap's [cursor.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/recording/src/cursor.rs) (fingerprint cursor image every tick, re-encode only on change, flush incremental files every 5 s with atomic renames for crash recovery).
- Write the event log as versioned JSON (moves, clicks, cursor-shape changes, key events, shell events, take markers) beside the media; this file is a product feature (§3), not an implementation detail.

### 5.2 Source recording format and the editor decoder (new)

**What the references do** (all read from source, 2 Nov 2026):

| Recorder | Codec / container | GOP | Bitrate rule | 4K data rate |
|---|---|---|---|---|
| Cap, default macOS Studio screen track (no camera) | FFmpeg `h264_videotoolbox` Main, realtime, into 2 s DASH `.m4s` fragments with 2 s timed `moof` flushes, byte-concatenated and stream-copied to a progressive `display.mp4` at Stop ([capture_pipeline.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/recording/src/capture_pipeline.rs), [PR #2646](https://github.com/CapSoftware/Cap/pull/2646)) | FFmpeg default 12 frames (0.2 s at 60 fps) because no `g` is set ([PR #2502](https://github.com/CapSoftware/Cap/pull/2502)) | 0.3 bpp × w × h × (30 + 0.6 × (fps−30)); Ultra 1.0 bpp; Compatibility 0.15 bpp | 75 Mb/s at 4K30 (34 GB/h), 119 Mb/s at 4K60 (54 GB/h), Ultra 398 Mb/s (179 GB/h) |
| Cap with camera active, camera tracks, Instant mode | AVFoundation `AVAssetWriter` H.264, non-fragmented MP4 (moov lost on crash) ([mp4.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/enc-avfoundation/src/mp4.rs)) | floor(fps × 0.75): 22 @30, 45 @60 (commit 3e30e64c, 6 Jun 2026, no rationale) | w × h × min(fps,60)/30 × 5 bits (Balanced, floor 8 Mb/s), ×10 Ultra (clamp 8–120), ×2.5 Compatibility; B-frames only in Ultra | 41.5 Mb/s at 4K30 (18.7 GB/h), 83 Mb/s at 4K60 (37 GB/h) |
| Reframed | HEVC Main10 (`AVVideoAllowFrameReorderingKey` false, `.mp4`) or intra-only ProRes 422/4444 (`.mov`); `expectsMediaDataInRealTime` true; no fragments ([EncodingSettings.swift](https://raw.githubusercontent.com/jkuri/reframed/main/Reframed/Utilities/EncodingSettings.swift)) | **Unset** — Apple: "the video encoder should choose where to place all key frames" | w × h × 5 bits (×7 HDR), no fps term | 41.5 Mb/s at 30 or 60 fps (18.7 GB/h); ProRes 422 at UHD 60p 1,178 Mb/s = 530 GB/h, 4444 = 1,193 GB/h ([Apple ProRes white paper](https://www.apple.com/final-cut-pro/docs/Apple_ProRes.pdf)) |
| Screen Studio | Unknown; 4.0 claims "up to 2× smaller" recordings *[not re-verified]* | unknown | unknown | unknown — see §8 |

**Decision.** A 60-minute 4K60 DevRel recording is 19–54 GB long-GOP versus 163 GB (ProRes 422 Proxy) to 1.2 TB intra-only, so intra-only is out; and the 12-frame GOP is an FFmpeg accident, not a design. Record:

1. **Codec:** hardware HEVC Main (8-bit; Main10 only for HDR) with H.264 as the compatibility fallback; drive `VTCompressionSession` directly so the keyframe and bitrate properties are honoured regardless of codec, and append the compressed `CMSampleBuffer`s to an `AVAssetWriterInput` created with `outputSettings: nil` (passthrough) — verify this path end-to-end in week one, since `AVVideoSettings.h` labels the equivalent `AVAssetWriter` keys "H.264 only" (§8).
2. **GOP:** set **both** `kVTCompressionPropertyKey_MaxKeyFrameInterval = fps × 1 s` (0.5 s when recording ≥ 4K60) **and** `kVTCompressionPropertyKey_MaxKeyFrameIntervalDuration = 2 s`. ScreenCaptureKit delivers only changed frames, so a frame-count-only GOP stretches to 20 s on a static screen (Cap measured 3 fps delivery and 60-frame = 20 s GOPs, [PR #2646](https://github.com/CapSoftware/Cap/pull/2646)); the duration cap bounds seek cost on static sections, and because §5.14's pacing repeats the last frame after 3 missed intervals the extra keyframes on static content cost at most one I-frame every 2 s. Cap's reason for not forcing keyframes ("a keyframe every 2 s of capture time grows a 1 fps recording 20×") is a bitrate concern worth measuring, not a correctness one.
3. **No B-frames:** `kVTCompressionPropertyKey_AllowFrameReordering = false`. This keeps the MP4 sample table's keyframe index (`stss`) usable and the file `ctts`-free, which is what lets the editor index keyframes without a packet scan (Cap's `container_keyframes()` falls back to a full scan when `video_delay > 0`, [avassetreader.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/video-decode/src/avassetreader.rs)).
4. **Bitrate:** start from w × h × min(fps,60)/30 × 5 bits for H.264 (Cap Balanced: 41.5 Mb/s at 4K30) and ~0.7× for HEVC (Reframed's w × h × 5 at any fps is 41.5 Mb/s at 4K), with a High tier at 2× and a Compatibility tier clamped to 2.5–10 Mb/s; tune on text-heavy UI with a legibility test, not PSNR alone (Cap retuned its formula once already, [PR #1732](https://github.com/CapSoftware/Cap/pull/1732)). BT.709 tags unless HDR.
5. **Container:** fragmented QuickTime/MP4 via `AVAssetWriter.movieFragmentInterval ≈ 2 s` so a crash, disk-full or dropped stream never loses the file (Cap's non-fragmented path "loses its moov (unrecoverable)"; its fragmented path lost >10 s on static screens until timed flushes, [PR #2646](https://github.com/CapSoftware/Cap/pull/2646)); at Stop, finalize to a progressive, faststart MP4 by passthrough export (`AVAssetExportPresetPassthrough`, as Reframed's `VideoTranscoder.swift` does) and keep the fragmented original until the finalize succeeds. Mark the project "needs finalize" if the app died mid-recording (Cap's `NeedsRemux` state).
6. **Storage:** check the destination volume's write throughput before recording and warn on external/SD media — Cap lost ~10% of a 38-minute 4112×2658 recording to I/O stalls on an SD card with 22–25 s whole-process freezes ([#2366](https://github.com/CapSoftware/Cap/issues/2366)); never block the capture callback on disk.

**Editor decoder.** Reframed's editor is a stock `AVPlayer` with ±1/600 s seek tolerance and a 60 Hz periodic observer, exporting through a sequential `AVAssetReader` on a core-count worker pool ([SyncedPlayerController.swift](https://raw.githubusercontent.com/jkuri/reframed/main/Reframed/Editor/SyncedPlayerController.swift)) — adequate for a small user base (none of its 17 issues is a scrub/decode report; its one export hang, a 57-minute recording stuck at 0%, was a click-sound generator, [issue #6](https://github.com/jkuri/Reframed/issues/6)), but it gives you no control over frame identity for a compositor that must match preview and export bit-for-bit. Build the Cap shape instead, specified from its code, not copied:

- A **keyframe index** read from the progressive MP4's sample table (cap `moov` parsing at tens of MB; a 60-minute 4K60 source has ~216k samples, [#3399 context](https://github.com/CapSoftware/Cap/issues/3399)), falling back to a packet scan for imported files with reordering.
- A **seekable reader** (`AVAssetReader` started at the keyframe at or before the request, reading to the end, `alwaysCopiesSampleData = false`; or a `VTDecompressionSession` fed by your own demuxer — untested, §8) fronted by a **frame cache with a byte budget** (Cap: 90 frames / 256 MiB; a 4K NV12 frame is 12.4 MB so 256 MiB holds ~21 frames = 0.35 s at 60 fps — the cache cannot substitute for a short GOP at 4K), a **reader pool positioned across the timeline** (5–8 readers, repositioned when a request lands > 5 s from a reader), a **scrub detector** (jump ≥ 5 frames, 100 ms cooldown), **10 cached frames below each backward seek** (halved frames decoded per backward-scrub step), **5 s idle-reader retention** (cut scrub-hunt decodes 1,858 → 547 and CPU 37.7% → 26.8%), a **cap of ~16 concurrent readers**, per-resolution **timeouts** (2–4 s normal, 10 s for the first frame after a seek) and an **automatic software fallback** ([decoder/avassetreader.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/decoder/avassetreader.rs), [PR #2868](https://github.com/CapSoftware/Cap/pull/2868), [PR #2986](https://github.com/CapSoftware/Cap/pull/2986)).
- **Check reader status on every empty read**: `AVAssetReader` can fail mid-stream with −11821 "Cannot Decode" when many VideoToolbox sessions run at once; Cap's decoder used to answer with stale cached frames (frame 106 served for 111) until it exposed the failure and recreated the reader ([PR #2872](https://github.com/CapSoftware/Cap/pull/2872)). Never return a cached neighbour as if it were the requested frame during export.
- **Budget from measurements:** a standalone `AVAssetReader` decodes 1080p60 H.264 at 0.36 ms/frame (p99 1.08 ms) on an idle M4 Max, 1.34 ms on a GitHub macos-15 M1 VM, and 54.5 ms/frame (257 ms p99) on a VM with all cores busy, where a 60-frame seek took 4.6–5.9 s ([PR #3366](https://github.com/CapSoftware/Cap/pull/3366)). Restart-from-keyframe at 60 fps therefore costs ~4 ms (12-frame GOP), ~16 ms (0.75 s), ~21 ms (1 s), ~43 ms (2 s) at 1080p and roughly 4× that at 4K (an assumption nobody has measured): only sub-second GOPs plus pre-positioned readers fit a 16.7 ms scrub budget at 4K60. Measure on your fixtures (§8).
- Cap's open macOS-only export bugs ([#1787](https://github.com/CapSoftware/Cap/issues/1787) stale/flickering frames, [#1940](https://github.com/CapSoftware/Cap/issues/1940) stuck on last frame) are reader-reliability problems, so add an export self-check: decode frame N, compare its PTS to the requested time, and fail loudly rather than emit a wrong frame.

### 5.3 Cursor smoothing
- Use a **spring-mass-damper solved in closed form per step** (under/critically/over-damped branches, rest snap at displacement < 1e-5 and velocity < 1e-4), simulated offline at 60 Hz into a timeline that render-time lerps. Phase-lead compensation: a spring chasing a moving target trails by `friction/tension` seconds, so sample the target that far ahead and ease the lead with a one-pole filter (~130 ms) on profile switches. Click anticipation: when the next click is ≤ 500 ms away the target becomes the click point; switch to a stiffer "snappy" spring (tension 530, mass 1, friction 40) 175 ms before the click; use a "drag" spring (1000/1/40) while a button is held. Pre-filter: drop direction reversals whose legs are both < 1.5% of the screen within 100 ms (accessibility-tool shake), decimate to ≤ 60 samples/s and ≥ 1/1920 UV travel, settle timeout 5 s, hold position on idle gaps > ~67 ms. Presets to start from (tension, mass, friction): Mellow 470/3.0/70 (Cap's default), Slow 200/2.25/40, Smooth 80/2.5/28, Fast 380/1.0/30 *(corrected: "fast" is a distinct preset, not an alias)*. Reference spec: Cap [cursor_interpolation.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/cursor_interpolation.rs) (1,974 lines) and [spring_mass_damper.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/spring_mass_damper.rs) (404 lines) *(corrected sizes)*; the closed-form derivation is Ryan Juckett's "Damped Springs".
- Simpler MIT alternative: Reframed's semi-implicit Euler at 1 ms substeps, presets slow/medium/fast/rapid = tension 80/170/300/500, friction 20/26/34/44, mass 3.0/1.5/1.0/0.6; stiffen ×min(zoom, 4) when zoomed > 1.05 and ×2 tension / ×1.5 friction during typing bursts; snap to click position and smoothstep-blend toward it over 0.1–0.3 s ([CursorSmoothing.swift](https://raw.githubusercontent.com/jkuri/reframed/main/Reframed/Editor/CursorSmoothing.swift)).
- For a live preview/follow mode use the 1€ filter (speed-adaptive low-pass; tune `fcmin` for jitter then `beta` for lag; reference implementations in Swift-portable C/Rust at [casiez/OneEuroFilter](https://gery.casiez.net/1euro/)).
- Ship Screen Studio's per-segment "disable smoothing" toggle: smoothing desynchronizes pointer from hover states (hub, Oct 2026), so dropdown fragments need raw motion.
- Draw the cursor **shape** from the raw (unled) timeline; shrink to 0.8× over ~130 ms on click; fade out after 2 s idle over 400 ms and fade back 250 ms before motion resumes; tilt up to ±0.35 rad with horizontal velocity; feather ~1 px at the display-card edge so an off-crop cursor slides off instead of popping (Cap [layers/cursor.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/layers/cursor.rs)).

### 5.4 Auto-zoom (two layers) — make every constant a user knob
- **Segment generation from events.** Click baseline: pad −300 ms / +2.5 s around clicks, merge intervals with gaps ≤ 2.5 s, ignore clicks in the last 1 s (the stop-recording click), default 2.0× auto / 1.5× manual (Cap [editor_edits.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/apps/desktop-gpui/src/editor_edits.rs)); or dwell-based clustering (clicks < 0.5 s apart merge, hold ≥ 0.5 s, 0.4 s transitions, overlapping regions merged with click-count-weighted centers — Reframed [ZoomDetector.swift](https://raw.githubusercontent.com/jkuri/reframed/main/Reframed/Editor/ZoomDetector.swift)); followcursor adds 3 s click windows, 4 s minimum gap, 0.15 spatial merge, 8 s cluster split, 100 ms anticipation, ≤ 4-cluster pan chains ([activity_analyzer.py](https://raw.githubusercontent.com/sabbour/followcursor/main/followcursor/app/activity_analyzer.py), MIT — note its `_dampen_pan` is dead code *(corrected)*). **Add the DevRel signals**: typing bursts (≥ 3 non-modifier keyDowns with gaps < 0.5 s), caret bounds (§5.13) and shell command boundaries (§5.13) as zoom anchors, and map all event times through trims/speed changes so zooms land on edited timelines (Cap 0.6.1).
- **Camera motion.** Three spring channels (center, amount, activity) retargeted every 8 ms with velocity carried across retargets — no fixed durations (stiffness 200, damping 40, mass 2.25 as a start). Dead zone: greedily cluster all cursor moves in the segment into boxes ≤ 50% × 70% of the zoomed viewport (÷ zoom amount); leaving the box re-aims the camera even without a click; focus = box center, fallback (0.5, 0.5). Keep the viewport inside the frame **by construction** (bounds from amount + center in 0..1 "travel space": 0 = flush left/top, 1 = flush right/bottom) and remap focus in the outer 25% band to the frame edge (`edge_snap_ratio 0.25`: [r, 1−r] → [0, 1]). Pre-aim: while amount ≤ 1.0005 snap the center instantly (invisible) so a zoom scales straight toward its focus instead of panning at magnification; hold the last framing during zoom-out; clamp amount ≥ 1 with velocity zeroed. Add tests for C1 continuity across segment boundaries and a precompute budget (Cap asserts a 30-minute, 50k-event project precomputes in < 500 ms). Reference spec: Cap [zoom_spring.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/zoom_spring.rs) (3,446 lines *(corrected)*) and [zoom.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/zoom.rs). Simpler MIT alternative: Reframed's quintic smootherstep `6t⁵−15t⁴+10t³` interpolated in 1/zoom space (visible size changes linearly) with a soft edge clamp `−t³+2t²` and follow margin `min(0.3, 1/(2·zoom)+0.05)` ([ZoomTimeline.swift](https://raw.githubusercontent.com/jkuri/reframed/main/Reframed/Editor/ZoomTimeline.swift)).
- Expose lead time, hold time, zoom level (including < 100%, a 63-vote Screen Studio request), follow speed, dead-zone size, and a Loupe-style "magnify without moving the frame" mode; Screen Studio users have asked for every one of these.

### 5.5 Motion blur (analytic, not accumulation)
- Cursor: a 21-tap directional box along the per-frame travel vector scaled by the user amount, fps-normalized (strength = amount × fps/60, clamped to 4), vector capped at 480 px to bound teleports; expand the sprite quad by the vector so the streak fits; output fully blurred — never crossfade with the sharp sprite ("reads as ghosting"); lift premultiplied color to straight alpha before color grading. Spec: Cap [cursor.wgsl](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/shaders/cursor.wgsl). CPU alternative: Reframed stamps ≤ 10 offset copies, speed from a 1/60 s finite difference, no blur below 30 px/s, magnitude = min(speed × intensity × 0.025, 60 px) ([CursorEffects.swift](https://raw.githubusercontent.com/jkuri/reframed/main/Reframed/Editor/CursorEffects.swift)).
- Screen pan: 21-tap directional kernel along the camera's per-frame motion in card UV, accumulating premultiplied color and alpha so the card edge smears too. Screen zoom: 13-tap radial kernel toward the zoom center, ray = distance × amount capped at 0.10 UV (real springs produce 0.03–0.05 at corners), weights 4(p−p²), per-pixel interleaved-gradient noise to hide banding; a zero-length kernel is the identity so blur fades with velocity and needs no ramp. Spec: Cap [composite-video-frame.wgsl](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/shaders/composite-video-frame.wgsl). Background: GPU Gems 3 ch. 27 and McGuire et al. 2012 (DOI 10.1145/2159616.2159639); accumulation (Haeberli & Akeley 1990) costs N full composites per frame and is unnecessary because the 2D camera transform is known analytically.

### 5.6 Backgrounds, padding, corners, shadow
- One Metal fragment pass over a signed-distance rounded rectangle (Euclidean corner, or superellipse power 4 for a squircle), per-corner radius multipliers (square the top corners against decorative chrome), 4× sub-pixel coverage with smoothstep AA; shadow = `smoothstep(size + blur, −blur, |d|) × opacity` with size/blur/opacity as uniforms (fractions of the smaller frame dimension); border via a second coverage at `size + borderWidth`; source-over in **straight** alpha (premultiply inside the blend) *(corrected)*; color grade (exposure, contrast, saturation, temperature, tint, vignette, grain) after compositing. Spec: Cap composite shader above; Screen Studio's controls to match: Padding (0 = no background), Rounded corners, Inset, Shadow angle/distance/softness, wallpapers, gradient generator, solid hex, custom image ([guide](https://screen.studio/guide/background)).
- Background blur: two-pass separable Gaussian, σ = strength × 2.5% of output height, radius 3σ, ≤ 24 taps per side with widened spacing and bilinear sampling (avoids comb patterns); σ scales with output height so preview matches export ([background-blur.wgsl](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/shaders/background-blur.wgsl)).

### 5.7 Click effects and sounds
- Ripple ring: radius `1 − (1−t)³`, width `0.10 + 0.06t`, alpha `(1−t)^1.5`, 0.6 s, default color (71,133,255), strength 0.7 ([click-ripple.wgsl](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rendering/src/shaders/click-ripple.wgsl)); Reframed adds a 0.14 s click bounce and sway up to π/18. Offer Screen Studio's Ripple/Circle/Shockwave variants and optional click sounds with volume ([guide](https://screen.studio/guide/mouse-click-sound)); keyboard sounds are an open Screen Studio request (70 votes). Generate click sounds lazily per export, not from the whole cursor log at once — Reframed's 57-minute export hung in exactly that step ([issue #6](https://github.com/jkuri/Reframed/issues/6)).

### 5.8 Camera bubble
- `AVCaptureSession` (720p/1080p/4K, target 30 fps), convert its PTS via `synchronizationClock` to the SCK/host timebase; composite as a layer with position, size, size-during-zoom, shape/roundness, mirror, crop; a dedicated layout timeline (overlay / fullscreen / split) with animated transitions; "smart framing" that moves the bubble away from the cursor (Screen Studio, CursorClip). Background blur/cutout is v2 (Cap uses ONNX via `ort`; Apple's Vision/segmentation is the native route — not researched). Reaction effects cannot be suppressed programmatically — detect `reactionEffectsInProgress` and tell users to disable Gestures in Control Center *(corrected)*. Record the camera as its own track in the same fragmented writer, same GOP policy as §5.2.

### 5.9 Keystroke overlay
- Group keyDowns with a 500 ms threshold, end groups on Space, linger 0.8 s, fade 0.15 s, reveal characters at their offsets with a 6 px bounce, keep ≥ 15 px from captions; show modifiers and special keys as symbols (Cap [keyboard.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/project/src/keyboard.rs); defaults size 50, bottom-center, black at 95%). Capture with two listen-only session-level `CGEventTap`s (keys; mouse + flags) as KeyCastr does ([KCEventTap.m](https://raw.githubusercontent.com/keycastr/keycastr/main/keycastr/KCEventTap.m), BSD-3); poll `tapIsEnabled` and re-enable on `tapDisabledByTimeout`. Secure-input fields: macOS withholds events from listen-only taps during secure input (KeyCastr README claim; verify). Screen Studio's heuristic that ignores rapid typing for single-key shortcuts is worth copying ([guide](https://screen.studio/guide/shortcuts)).

### 5.10 Typing speed-up and keystroke re-timing (differentiator)
- Detect typing bursts as in §5.3; offer per-segment speed and "apply to all typing parts" like Screen Studio ([guide](https://screen.studio/guide/speed-up-typing-segments)); then go further: re-time each inter-key interval to a uniform cadence (with small variance), collapse backspace runs, and — for terminal targets — optionally re-render typed text from the keystroke log. Scripted precedents: VHS `TypingSpeed`, webreel `charDelay` ([webreel](https://github.com/vercel-labs/webreel), Apache-2.0).

### 5.11 Captions, transcript editing, silence and filler removal
- Captions: WhisperKit (Reframed) or Apple Speech (Screen Studio's path on macOS 26+), word-level timestamps, caption styles with word animations, SRT/VTT that follows cuts and speed changes; bias the decoder with on-screen vocabulary (OCR of window text, shell-log commands) and an unlimited project vocabulary — Descript's bar is 30 glossary terms per Drive, English only, auto-added after three identical corrections ([help](https://help.descript.com/script-editing/transcription-glossary.md)). Remotion's whisper.cpp recipe (`tokenLevelTimestamps` via `--dtw`, whisper.cpp ≥ 1.5.5) is a reference for word timing ([docs](https://www.remotion.dev/docs/install-whisper-cpp)).
- Silence detection: Silero VAD v6.2.x (MIT — LICENSE verified): 16 kHz, 512-sample (32 ms) windows, threshold 0.5, `neg_threshold = max(threshold−0.15, 0.01)`, min speech 250 ms, min silence 100 ms, pad 30 ms, < 1 ms per chunk on one CPU thread; resample 48 kHz audio first ([utils_vad.py](https://raw.githubusercontent.com/snakers4/silero-vad/master/src/silero_vad/utils_vad.py)). Cheap baseline: auto-editor's per-frame peak detector (max|sample|/32767, 4% threshold, 0.2 s margin, Unlicense) ([audio.nim](https://raw.githubusercontent.com/WyattBlue/auto-editor/master/src/analyze/audio.nim)); WebRTC VAD accepts 48 kHz directly but gives no probability.
- Filler words: stock Whisper drops "um/uh", so transcribe with a verbatim-biased prompt; slide each cut edge ≤ 60 ms to an RMS minimum then to a zero crossing without crossing neighbor words; merge fragments < 120 ms; crossfade 0.15 × cut clamped 50–120 ms; offer "remove" (shrinks timeline) vs "silence" modes; re-transcribe to validate (erm, MIT, [repo](https://github.com/dougcalobrisi/erm)). Copy Descript's review UX, not its auto-apply: list every candidate with timestamp and audio preview and per-item Delete / Delete-and-gap / Ignore / Remove-from-transcript, plus an "avoid harsh cuts" check that skips cuts that would clip neighbouring words ([help](https://help.descript.com/script-editing/filler-words.md)). Screen Studio only added filler/pause removal in 4.0 and requires cloud transcription for it; whether Cap/Reframed lack silence removal entirely is *(unverified)*.

### 5.12 Secret redaction (differentiator)
- Per-frame on-device OCR (Apple Vision text recognition, as Censr does) + regexes for keys/tokens/emails/phones/cards + a team hide-list; track detections across frames so covers follow scroll and typing; check the keystroke log so a typed key is masked before OCR sees it; adaptive mask color from covered content (Screen Studio 4.0); "Review before sharing" report listing every detection. Masks that don't follow scrolling and single-layer limits are live Screen Studio complaints ([guide](https://screen.studio/guide/adding-a-mask-and-highlight), [hub](https://hub.screen.studio/p/multiple-mask-layers)). Behavior target: Screen Studio 4.1 as described by [AlternativeTo](https://alternativeto.net/news/2026/10/screen-studio-4-1-introduces-privacy-features-prores-export-and-faster-mp4-and-gif-exports/) (secondary source).

### 5.13 Terminal/IDE awareness: caret zoom, command callouts, chapters (differentiator)
- Shell integration: ship a tiny zsh/bash/fish hook that logs `{timestamp, cwd, command, exit code}` on preexec/precmd into the event log, and consume OSC 133 semantic marks (A prompt start, B prompt end, C command start, D command end + exit status) emitted by iTerm2, WezTerm, Ghostty and Kitty — note marks carry no command text in iTerm2/Ghostty, not all shells send B, Ghostty emits bare D on empty Enter, iTerm2 embeds a CR in C ([WezTerm docs](https://wezterm.org/shell-integration.html)). Render a styled command chip at C and a status badge at D; expose copyable commands and chapters.
- Caret bounds: `AXFocusedUIElement → AXSelectedTextRange → AXBoundsForRange` works in native text fields, is patchy in Electron/browser surfaces, and Ghostty's AX support is still a draft ([PR #10992](https://github.com/ghostty-org/ghostty/pull/10992)); fall back to window bounds + cell metrics + the cursor row from shell integration, or OCR of the prompt region. Screenize (Apache-2.0) is the only open reference for AX-based UI-element zoom.

### 5.14 A/V sync, VFR and crash safety (copy Cap's hard-won mechanisms)
- One monotonic time base (mach_absolute_time); snap stream start times together when they differ by > 30 ms (fixed 86–125 ms display/camera drift); rebase device audio clocks that are > 5 s off; compensate measured mic input latency; detect audio gaps by expected PTS and fill with silence ([Nonstrict](https://nonstrict.eu/blog/2024/handling-audio-capture-gaps-on-macos)); on high-refresh displays gate frame cadence with an EMA of inter-frame deltas (enter decimation at 0.88× nominal interval — "about 14% fast" *(corrected)* — exit at 0.95×); repeat the last frame only after 3 missed intervals; stamp frames with capture time, never dequeue time (Cap [#2144](https://github.com/CapSoftware/Cap/issues/2144): frames waited in a 15-slot channel plus a 50 ms stall budget and were written 100–300 ms late while cursor.json kept true times); on open, losslessly re-stamp tracks recorded at the wrong rate. Write fragmented files (§5.2) so a dropped stream never loses the file, and implement `stream(_:didStopWithError:)` with auto-restart. Build the clapperboard self-test on day one: a page flashes white and clicks every 2 s; analyze flash/click pairs for drift slope (< 10 ms/min excellent, > 30 investigate) ([scripts/av-sync](https://raw.githubusercontent.com/CapSoftware/Cap/main/scripts/av-sync/README.md), [FINDINGS.md](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/recording/FINDINGS.md), [cadence.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/recording/src/sources/screen_capture/cadence.rs)). The report's "mixer drift 0.1–0.36 s over 30–60 min" figure has no source and is dropped. Expect pause/resume and VFR to be the largest bug source in the writer: Cap's `mp4.rs` needed repeated PTS-monotonicity and pause-timing fixes from May to Aug 2026.

### 5.15 Export and GIF
- `AVAssetWriter` with VideoToolbox hardware H.264/HEVC/ProRes, `RealTime = false`, `PixelBufferReceiver` on 26+ / adaptor on 15.x; start the session at the first frame's PTS and end at the last; size in pixels; `hevcWithAlpha` for transparent exports; cursor-only ProRes 4444 for compositors; estimate size/time and guard low disk/memory before starting (Cap 0.6.0); **export keyframe interval 2 s** rather than every 12 frames (Cap's exports were up to 3× oversized at the FFmpeg default, fixed in [PR #2502](https://github.com/CapSoftware/Cap/pull/2502); its 93 MB → 30 MB 4K-minute figure comes from the same change); HEVC hardware export is a user expectation now (Cap [PR #3623](https://github.com/CapSoftware/Cap/pull/1732), 1 Nov 2026 — cited via the preset history in PR #1732); faststart; make preview and export the same Metal pass.
- GIF: either gifski (quality 1–100, default 90, `fast=false`, 30 fps; cross-frame palettes and temporal dithering; **AGPL-3.0-or-later** — run the CLI as a separate process or buy a commercial license; [gifski](https://github.com/ImageOptim/gifski)) or FFmpeg `palettegen`/`paletteuse` (LGPL): default dither `sierra2_4a`; `bayer` or `none` for flat UI; `stats_mode=diff` + `diff_mode=rectangle` for mostly static screens; shrink width/fps/duration before touching colors ([filters.texi](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/filters.texi)). ImageIO's GIF writer clamps frame delay to 100 ms — unusable above 10 fps. Cap shipped GIF export in 0.3.53 (Jul 2025) and transparent GIFs in 0.3.78 (Oct 2025) *(corrected)*.

### 5.16 Voice enhancement and loudness ("Studio Sound", new)
- **Reference to study (behavior only, AGPL):** Cap's Studio Sound, added 12–13 Sep 2026 ([commit 1078040](https://github.com/CapSoftware/Cap/commit/1078040)): a vendored copy of xiph/rnnoise pinned to the 22 Feb 2025 upstream commit, built with `cc` at −O3 with `USE_WEIGHTS_FILE`, runtime SSE4.1/AVX2 dispatch on x86 and the portable core on Apple silicon ([build.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/rnnoise/build.rs)); a `VoiceEnhancer` running one `DenoiseState` per channel (1–2 ch) on 480-sample / 48 kHz frames, samples scaled by 32768, output = 90% denoised + 10% delay-aligned dry, the 960-sample (20 ms) filter delay compensated, VAD probability > 0.6 used only to count speech frames ([voice.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/audio/src/voice.rs)); then a leveler that measures integrated loudness with ffmpeg's `ebur128` over up to 8 windows from the first 16 s (needs ≥ 20 speech frames, else a default profile), gain = (−16 − measured) clamped −12…+24 dB, `acompressor` ratio 2 / attack 15 / release 180, makeup clamped ±6 dB, then an `alimiter` at 0.841395 (≈ −1.5 dBFS) oversampled to 192 kHz ([voice_level.rs](https://raw.githubusercontent.com/CapSoftware/Cap/main/crates/audio/src/voice_level.rs)); applied non-destructively in the editor/export path behind "Studio Sound" and "Studio Sound for new recordings" toggles.
- **Approach for v1 (Swift):** compile xiph/rnnoise (BSD-3-Clause; 48 kHz mono frames of `rnnoise_get_frame_size()` = 480 samples; `rnnoise_process_frame` returns the VAD probability; v0.2 tagged 15 Apr 2024, last commit 22 Feb 2025, [repo](https://github.com/xiph/rnnoise)) into the app, run it per channel on the mic track only (never on system audio), keep the 90/10 wet/dry blend and delay compensation as defaults with a strength slider, and implement BS.1770 integrated loudness + gating in Swift (or call a bundled LGPL ffmpeg's `ebur128`) to level to **−16 LUFS integrated with a true-peak ceiling of −1 dBTP**: Apple Podcasts requires −16 LKFS ±1 dB and ≤ −1 dBTP ([spec](https://podcasters.apple.com/support/893-audio-requirements)), Cap targets −16, Descript Auto-leveling targets "about −16 dB" ([help](https://help.descript.com/effects-animations-transitions/auto-leveling.md)). Presets: "Streaming −14" (Spotify normalizes to −14 LUFS and asks for ≤ −1 dBTP, [Spotify](https://support.spotify.com/us/artists/article/loudness-normalization/); YouTube's −14 is community lore — Google's upload guide specifies only codec/bitrate, [YouTube](https://support.google.com/youtube/answer/1722171)) and "Broadcast −23" (EBU R128 v5: −23 LUFS ±1 LU, −1 dBTP, [R128](https://tech.ebu.ch/docs/r/r128.pdf)). If you use ffmpeg's `loudnorm`, override its defaults (I = −24, LRA = 7, TP = −2) and run two passes with the `measured_*` values ([filter docs](https://ffmpeg.org/ffmpeg-filters.html#loudnorm)). Store the target in the brand kit (§3 row 7).
- **v2 quality option:** DeepFilterNet (code dual MIT/Apache-2.0; 48 kHz, 20 ms windows / 10 ms hop, 2-frame lookahead = 40 ms latency or the no-lookahead "ll" model at 20 ms; real-time factor 0.19 single-threaded on an i5-8250U; pure-Rust `tract` inference with a C API feature; [paper](https://arxiv.org/abs/2305.08227), [Cargo.toml](https://raw.githubusercontent.com/Rikorose/DeepFilterNet/main/libDF/Cargo.toml)). It has de-reverb that RNNoise lacks, but the repo's last commit is 17 Oct 2024 and crates.io is frozen at 0.2.5 (2022) ([commits](https://github.com/Rikorose/DeepFilterNet/commits/main)), so vendor libDF at a pinned revision as Cap does with RNNoise, and confirm the weights' license first (§8).
- **Optional live stage:** `AVAudioEngine` voice processing on the mic input node (AEC/NS/AGC) for users who also play system audio through speakers; it is live-only, Mac-only and constrained (§4.1), so keep the export-time stage as the one that defines the sound. Descript's Studio Sound is the thing to beat: cloud-processed, "requires an internet connection", credit-metered, and it can flatten the waveform under loud noise ([help](https://help.descript.com/effects-animations-transitions/studio-sound.md)).

### 5.17 Multi-take stitching and retake detection (new)
- **Record-time structure first.** A marker hotkey (and optional voice/clap marker, as Stripe's crew used) writes `take_start`/`take_end` events into the event log; a countdown-free "retake from here" re-arms the recorder on the same timeline. Descript users explicitly asked for a spoken or clicked retake marker because repeated takes degrade transcription ([feedback, 9 May 2025](https://feedback.descript.com/feature-requests/p/retake-markup-button-or-voice-for-better-retake-text-recognition-transcription)); markers make detection a lookup instead of a guess.
- **Detection when markers are missing.** Transcribe (§5.11), then compare consecutive sentence-level spans with a word-sequence similarity (e.g., normalized edit distance over tokens with a lookback window of ~3 candidate spans and a minimum match of ~70% of the longer span — tunable, no published numbers exist, since Descript documents only that it "detects where you've re-recorded a phrase and marks earlier versions for removal", [help](https://help.descript.com/descript-tour/sound-good-tools.md)); add an audio-similarity fallback (MFCC/DTW over the candidate spans) so a mangled transcript of take 2 still matches take 1.
- **Selection rule: one contiguous take wins** — by default the last take whose span is complete; never splice words from several takes into one sentence (the complaint that Descript's output "sounds really choppy" when one sentence has 3–4 cuts, [feedback](https://feedback.descript.com/feature-requests/p/use-one-retake-instead-of-multiple-cuts-1)).
- **Boundaries.** Trim silence at take edges with Silero (§5.11), snap cuts to RMS minima/zero crossings (erm's rules), optional 50–120 ms crossfade or Cap-style crossfade transition; carry zoom/caption/camera-layout state across the join; re-solve zooms on the edited timeline (Cap 0.6.1).
- **Review UX.** A candidate list with next/prev, A/B preview of kept vs removed take, accept/reject per candidate, and a persisted list (Descript's disappears when the app closes) — the Aug–Sep 2024 complaint that made Descript's tool "almost impossible to use on long podcasts" ([feedback](https://feedback.descript.com/feature-requests/p/remove-retakes-needs-next-prev-to-preview-before-committing-the-change)). Competitors to benchmark: Tella "Remove mistakes" (semantic, user-confirmed), Cap merge/clips/crossfades, Remotion Recorder silence trim per take.

## 6. Open-source, licensing and distribution guidance

**License and governance.** Apache-2.0 (express patent grant and trademark clause; permissive so other companies' DevRel teams can adopt — Google, for example, bans AGPL internally ([policy](https://opensource.google/documentation/reference/using/agpl-policy))); a desktop recorder has no SaaS-capture problem for AGPL to solve. DCO sign-off (`git commit -s`, DCO Probot) rather than a CLA unless the company wants relicensing optionality (OpenStack replaced its CLA with DCO effective 1 Jul 2025 *(corrected date)*, [resolution](https://governance.openstack.org/tc/resolutions/20250520-replace-the-cla-with-dco-for-all-contributions.html)); Contributor Covenant 3.0 (text is CC BY-SA 4.0, [v3.0](https://www.contributor-covenant.org/version/3/0/code_of_conduct/)); MAINTAINERS/GOVERNANCE from GitHub's [MVG](https://github.com/github/MVG); a TRADEMARKS.md modeled on [ASF's policy](https://www.apache.org/foundation/marks/); trademark clearance (USPTO Trademark Search replaced TESS on 30 Nov 2023, WIPO Global Brand Database, EUIPO TMview) before announcing a name, and keep location-attributed evidence of use if you register (Deepkit reportedly lost its EU mark in 2025 for lack of provable EU use — [Gigazine](https://gigazine.net/gsc_news/en/20250815-small-oss-project-trademark), secondary source).

**Code-reuse map.**
- MIT, reusable with attribution: `scap` ([repo](https://github.com/CapSoftware/scap)), OpenScreen, Reframed, Kap, VHS, `windows-capture`, ScreenForge, Cap's `scap-*`/`cap-camera*` crates, Silero VAD (model + code; LICENSE verified), erm.
- BSD-3-Clause: xiph/rnnoise (library and the weights blob Cap vendors, upstream COPYING retained), nnnoiseless (Rust port), KeyCastr.
- Apache-2.0: Screenize, Vuoom, Open Recorder, GPUI, webreel. DeepFilterNet code is dual MIT/Apache-2.0 but its model weights carry no separate license statement — confirm before bundling (§8).
- **AGPL, spec-only:** Cap's main codebase (and its distributed binaries need a commercial license for commercial use), Recordly (plus naming/attribution clauses *(corrected)*), OpenScreenStudio, QuickRecorder, gifski, asciinema (GPL-3.0). GPLv2: gifsicle. No license at all: obs-zoom-to-mouse, SmoothCursor. LGPL-style: libuiohook.
- **Clean-room discipline** (the 2026 chardet LGPL→MIT dispute is the reference case): whoever reads Cap's code writes specs and tests (this §5 is that spec), implementers work from specs and permissive references, keep contemporaneous provenance (design docs, commit history, AI-assistant prompts and transcripts), never copy Cap's UI strings, assets, project-file format or names ([Willison](https://simonwillison.net/2026/Mar/5/chardet/), [Meeker](https://heathermeeker.com/tag/lgpl/), [Reed Smith](https://www.reedsmith.com/our-insights/blogs/technology-law-dispatch/102nbig/clean-room-coding-in-the-age-of-ai-who-owns-the-code/)). Clean rooms do not defend against patents.

**Codecs.** Encode H.264/HEVC through VideoToolbox — you ship no encoder; FFmpeg, if bundled at all, only as an LGPL build (no `--enable-gpl`, no x264/x265; OpenScreen links BtbN "lgpl-shared" builds for this reason). Patent posture: Via LA's AVC program charges $0 for the first 100,000 units/year per affiliated group, $0.20 thereafter, but does not define whether a free download is a "unit", and no written Apple statement covering third-party VideoToolbox use was found ([Via LA](https://www.via-la.com/licensing-2/avc-h-264/), [forum 767543](https://developer.apple.com/forums/thread/767543)) — counsel question. HEVC: Access Advance acquired Via LA's HEVC/VVC pool (Dec 2025, now "VCL Advance"), its rate card is public ("All HEVC Software" $1.00/$0.50 per copy; royalties due for software sold separately from a device; cloud services pay per authorized user), and the announced 25% increase was postponed with a lock-in deadline of 30 Jun 2026 *(corrected; [program overview](https://accessadvance.com/wp-content/uploads/2025/07/HEVC-Advance-Program-Overview-July-2026.pdf))*; whether an app that only calls the OS HEVC encoder is "HEVC Software" is an inference to confirm with licensing@accessadvance.com — this matters more now that §5.2 recommends HEVC as the source codec (H.264 is the fallback if counsel says no). AV1: SVT-AV1 is BSD-3-Clause-Clear + the AOM royalty-free patent license ([PATENTS.md](https://gitlab.com/AOMediaCodec/SVT-AV1/-/raw/master/PATENTS.md)), but Apple silicon through M5 has hardware AV1 decode only (no VideoToolbox AV1 encoder exists in FFmpeg's codec list; [specs](https://www.apple.com/macbook-pro/specs/)) and Safari plays AV1 only with hardware decode (M3+) — keep AV1 an opt-in preset. Cisco's OpenH264 binary license covers only a separately downloaded, user-toggleable, attributed binary — relevant only to future Windows/Linux builds ([license](https://www.openh264.org/BINARY_LICENSE.txt)). GIF: gifski AGPL (process boundary or commercial license) vs FFmpeg palette path (LGPL).

**macOS distribution.** Developer ID Application certificate, Hardened Runtime, `com.apple.security.device.camera` + `.audio-input` entitlements, secure timestamp, no `get-task-allow`, `xcrun notarytool submit --wait` then `stapler staple` (staple the .app and the DMG; ZIPs cannot be stapled; 75 notarizations/day; most complete within 5 min) ([Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)); `create-dmg` can sign and notarize the image in one step. Sparkle 2.10.x with EdDSA appcast (`SUFeedURL`, `SUPublicEDKey`, `generate_appcast` deltas; macOS 12+) — updater keys and notary credentials are company assets, plan their transfer in the exit plan (Atom's certificate revocation bricked installed versions, [GitHub](https://github.blog/2022-06-08-sunsetting-atom/)). Homebrew cask: developer-published download, must pass Gatekeeper, `zap` stanza, `auto_updates true` when Sparkle is present, notability ≥ 30 forks / 30 watchers / 75 stars (90/90/225 if self-submitted), repo ≥ 30 days old ([policy](https://docs.brew.sh/Package-Acceptance-Policy)). Permission UX: expect the periodic re-consent for non-picker capture and the one-time grant + relaunch (§5.1); the MDM key `forceBypassScreenCaptureAlert` (15.1+) helps on the company's own managed Macs ([Restrictions](https://developer.apple.com/documentation/devicemanagement/restrictions)) — ask IT whether it is acceptable. Mac App Store is feasible later (a ScreenCaptureKit recorder, Recorder.app, ships there) but requires sandboxing, forbids Sparkle and self-updating code, needs a visible recording indicator (2.5.14), blocks Accessibility (use `CGEventTap`), and forbids license-key screens — treat as a reduced-feature variant, not the primary channel. Telemetry etiquette: opt-in analytics only and no background downloads without consent (Screen Studio's auto-updater incident is the cautionary tale).

**Maintenance and exit.** Name a maintainer-of-record and a funded maintenance budget before launch (Kap decayed within two macOS releases; its last release still bundles an EOL Electron 13); run the public build internally rather than a private fork (Spotify called regaining Backstage parity "heart surgery", [LeadDev](https://leaddev.com/software-quality/bringing-internal-engineering-projects-world)); document a hand-off path (OpenScreen's creator archived the repo and a community org continued it with approval; Fig's `withfig/fig` repo was archived in Mar 2025 after the AWS acquisition *(corrected)*).
